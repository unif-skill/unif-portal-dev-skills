# 工程技能入口

采用本插件共用研发规范的 RN／原生鸿蒙 Portal 或对应 @unif 库工程，可在已有 AGENTS.md 中合入以下入口，并随工程所选技能版本维护。只安装单个库能力技能的工程沿用自己的规范，无需合入整套阶段入口：

```markdown
## 技能使用

按当前请求要完成的工作选择企业入口。事实查询、版本核对和已有接口说明按问题取得资料，不因读取源码就进入开发或代码审查；正式审查和架构设计即使不改文件，仍使用对应入口。

- 实现、调整或排查客户端及库代码时使用 code-development：先确定 RN／原生鸿蒙及应用／库／共享核心，RN 按变更选择工程主题及“库开发”，鸿蒙选择“鸿蒙适用范围”及所需文件、状态、UI、接入与测试专题；对应库能力技能与 H5 桥接按实际涉及范围读取。开发 RN 库文档站、组件 Web 示例或 LiveDemo 时读取“文档站开发”；鸿蒙库使用文档与原生示例读取鸿蒙“文件与公共入口”和“测试与验收”，沿真实 ArkUI 宿主验证；仅改组件内部或原生能力且不影响网站时不加载该专题。iOS 真机安装、Metro 热刷新及设备调试连接恢复读取“真机调试”，仅为用户准备手测也适用；现场参数和有效交接按当前任务复用。
- 实现、调整、组织或排查 Python 后端时使用 backend-development，按实际任务选择目录、依赖、运行资源及契约验证主题。
- 模块职责、公共契约、状态归属或场景组合变化使用 architecture-design；内部等价修改沿用有效设计。
- 使用对应 RN 包时选择 unif-design、unif-chat、unif-camera、unif-hms-scan、unif-umeng 或 unif-icons，读取所需公开 API、版本与任务指引；组合需求只加载实际相关的能力。单纯接口查询可以直接使用能力技能，不启动开发阶段。
- 设计、编写或执行测试使用 code-testing。
- 对明确代码变更做审查时使用 code-review。
- 准备或执行提交、推送、PR/MR、合并、发布与清理，或核对其交付条件时使用 code-delivery，按任务授权执行。

新建 @unif RN 库、工程标准尚未接入或首次／恢复发布时，按需读取 code-development 的“新库接入”，从组织标准仓取得有效依据并对照本工程实际配置；普通维护沿用有效接入记录，不重新初始化工程。原生鸿蒙 HAR 按其原生规则与实际 OHPM 标准处理；六个 RN 能力技能不提供 ArkUI API。

原生六库从 code-development 的 harmony-icons、harmony-design、harmony-chat、harmony-camera、harmony-hms-scan、harmony-umeng 专题按需取得规范；应用消费、HAR 维护、共享核心分别选择资料。专题是目标契约和验收依据，实际 API 以所采用原生库导出和 SDK 为准。图标及设计资源同源生成，应用字号只缩放一次；地图／POI 使用高德，统计与分享使用友盟。

同一上下文已经读取且仍适用的入口、规则与契约直接复用；阶段转换只补新增职责所缺的依据，来源或范围变化只补相关部分。独立子任务取得自身需要的正文，不仅依赖父任务的读取声明。读取其他技能提供的规则不等于启动其工作阶段。

规范版本采用本工程指定的来源或锁定的技能快照，任务明确指定版本时以该版本为准。通用流程不能替代企业要求，也不因已加载而扩大本次任务；检查命令、CI 门禁和发布约定由本工程维护。
```

项目可在现有依赖或交付约定中锁定插件版本或 Git 提交，并指明规范根目录或可访问的修订；不在 AGENTS.md 复制类型、常量、命名和目录规则。code-development 的完整目录包含RN／鸿蒙规范快照和按需专题，可单独分发；库能力技能的完整目录同样可独立分发；应用消费从库官网和采用版本的公开类型取得依据，源码维护与 H5 契约从工程指定规范取得。平台原则由 architecture-design 提供，或采用目标工程的规范，不依赖其他技能的私有文件路径。架构规范及其 spec 仍由 `unif-platform-architecture` 项目维护。

库工程保留自身目录、构建、原生配置及发布约定，不能因使用同一个技能而套用 Portal 的业务目录。应用仅消费已发布组件时，核对采用版本的公开接口与接线；需要修改库源码时才加载库维护资料。目标组件契约与当前发布包能力分别核对。

code-testing、code-review 与 code-delivery 只维护阶段所需的规范入口，与 architecture-design、code-development、backend-development 一同分发。它们按需取得共同规范，不把规范提供者当作必须重复进入的阶段。测试质量、文件规则和验证责任由规范源维护，具体命令、门禁及版本发布约定由目标工程维护；不另写通用 TDD、审查或 Git 流程。

旧 Portal 的旧目录与技能只服务其对应工程，按项目安装和读取。新工程采用上述入口，不把旧 `portal`、`rn-library`、`git-flow` 或 `test-quality` 作为本插件的隐式依赖；其他 SDK 按当前能力契约、采用版本的公开类型和文档核对，不因一个库新增 API 自动再建技能。

没有既定流程时仍按企业技能完成对应工作，不要求另装流程插件。复用已有结果前核对其是否覆盖当前变更和企业要求；有遗漏时补齐对应工作，不能因通用流程已经运行而跳过企业规范。

技能仓默认校验覆盖技能格式、包内引用、市场入口和生成资料；本地评测摘要可按[仓库验证说明](../README.md#验证)选择检查。同步工具及其测试验证快照生成与来源检查。这些检查没有扫描目标工程的 TS／TSX／ArkTS，也没有启用其文件角色或导入门禁。

RN 目标工程接入时，在其已有 TypeScript、ESLint 和静态分析配置中落实可确定的类型、命名、导入方向、私有深路径、循环依赖与角色文件检查。需要区分固定值和运行期内容时使用 AST 与作用域信息；业务含义、资源归属和副作用仍按契约审查。测试按实际消费者、宿主和协议影响选择。这些是待目标工程接入的检查，不随技能安装自动生效。

后端工程通过现有 Ruff、mypy、pytest 和契约生成检查落实规则；目录与依赖检查随工程测试执行。backend-development 的规范源为架构仓 BACKEND_DEVELOPMENT.md，使用 sync_architecture.py 的同名 --skill 入口同步。技能候选、发布与安装状态分别核对。

原生鸿蒙工程声明实际采用的规范源与技能修订、SDK／API 目标、库与应用边界、共享资源来源及验证命令。按实际工具接入 ArkTS 类型、依赖、HAR 产物与宿主测试；原生构建、设备和业务证据分别记录。规范候选可作为任务明确采用的本地依据，不能标为已发布安装版本；项目入口不复制整套规范。

外部鸿蒙技能只补平台知识和工具用法，按工程采用清单与锁定记录选择，不自动恢复归档项。规范／技能任务完成不自动启动原生库、应用或示例开发；实施、提交、发布和安装仍依据当前任务授权。
