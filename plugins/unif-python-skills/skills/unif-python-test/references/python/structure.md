## 2. 目录与文件归属

Python 服务采用 api、core、db、services、schemas、utils 六类外层目录，内部按实际能力归组。服务包根只保留包入口和应用／进程入口，如 `__init__.py`、`main.py`、`worker.py`；既有部署入口 `app.py` 按工程采用。仓库级契约源、tests、sql、依赖锁及部署配置保持原有角色。

| 目录 | 承担内容 | 边界 |
|---|---|---|
| api | 路由挂载、请求身份交接、请求／响应校验、HTTP/SSE 和错误映射 | 对外路由集中在 api/routes，调用服务完成操作，不维护另一套业务规则 |
| core | 配置、身份与权限基础规则、错误定义、安全诊断、日志 | 不依赖具体服务、数据库实现或 HTTP 路由，不收纳实际业务流程 |
| db | MySQL／Redis 连接、数据读写、事务与持久化约束 | 按存储与数据职责组织，保留原子性和执行资格校验，不反向调用服务或路由 |
| services | 实际能力及操作协调、任务生命周期、外部系统接入 | 按能力分组，不为每个接口创建只转发参数的 service 包装 |
| schemas | 输入输出定义、协议加载与校验、同源生成产物 | 公开契约继续从所属 contracts 生成，禁止另建手写同义 DTO；数据库建表语句归 db 或部署 sql |
| utils | 多个模块确实共用、没有网络／数据库副作用的纯函数 | 单一能力的辅助函数留在原模块；不容纳认证、客户端、查询、匹配或运行流程 |

`services` 内部区分智能体能力、运行机制和外部通信：

- `agent`：所属智能体的路由或任务理解、上下文投影；Skill、提示词和模型工具分别归入 `skills`、`prompts`、`tools`。Agent 的小U只决定助手路由，Marketing 自行维护业务任务识别与提示词。
- `execution`：受理、领取、执行、暂停恢复、取消、结果采用和资源收尾。入口共同装配的资源可归本单元，实例所有权不因复用而合并。
- `clients`：模型供应商、领域助手和解析服务等外部通信。客户端负责技术请求、响应和连接收尾；工具声明、允许的语义动作及选择校验由所属 agent 能力维护并显式传入。
- `attachments`、`memory`、`speech` 等：按实际能力保留规则与协调。同一能力的 HTTP、持久化和协议分别进入 api、db、schemas；不机械拆散同一事务或重复维护状态。

上述子目录按真实职责采用，不要求服务具备全部能力。小模块先用单个文件，有可独立维护的职责再拆目录；不预建空类型、常量、辅助类或备用入口。纯函数可以在实际公共复用时进入 utils，不按名字相似强行合并。

环境配置沿用所属工程分层。Agent 与 Marketing 联合部署时，共享模型配置与服务间密钥由 Agent 根配置提供；认证、数据库、服务地址和运行限制等专有项归各服务配置。环境变体保留对应基础配置的目录层级，不因目录迁移或部署便利改变配置来源。


## 3. 公共入口与依赖

应用／进程入口组装具体依赖，管理启动和关闭。api 调用 services；services 按需要使用 db、schemas、core、utils。db 不依赖 api 或 services；core、schemas、utils 不反向依赖上层，utils 不依赖项目其他层。schemas 可使用 core 的错误定义及 utils 的纯函数，core 不反向加载 schemas。services/clients 不依赖 agent、execution 或其他服务能力，具体操作规则由调用方传入。

同一能力内部使用明确的具体模块，跨能力通过实际需要的稳定公共入口。`__init__.py` 只导出需要的接口，不创建连接、运行任务或安装路由；不为缩短导入路径层层转导。不存在真实消费者的旧路径在迁移后删除，不保留空兼容包或动态别名。

模型客户端只负责技术通信，不包含下单、拜访等领域流程。Skill、提示词、工具定义和上下文投影留在所属智能体能力；普通后端函数不会因为位于 tools 就自动成为模型工具。模型工具应有明确声明、参数校验与执行适配，运行代码仍执行授权、来源和结果校验。商品记忆候选及业务数据归属继续按已确认业务契约，不因分层改变匹配责任。

消费者通过参数提供外部依赖，测试可替换相同边界。`api → services → db` 表示职责方向，不要求每个请求都经过一个新增的转发函数。禁止为了目录形式引入动态扫描、通用注册中心、同义类型或无实际需要的框架。
