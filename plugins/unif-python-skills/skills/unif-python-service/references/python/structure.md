## 2. 目录与文件归属

Unif Python 服务按实际职责采用 api、agent、capabilities、core、db、services、schemas、utils。agent、capabilities 与 core、services 同级。以下目录规则用于本规范采用的 Python 服务，目录只在有实际模块时创建。服务包根保留包入口和应用／进程入口，如 `__init__.py`、`main.py`、`worker.py`，既有 `app.py` 按工程采用。仓库级契约源、tests、sql、依赖锁及部署配置保持原有角色。

| 目录 | 承担内容 | 边界 |
|---|---|---|
| api | 路由挂载、身份交接、请求／响应校验、HTTP/SSE 和错误映射 | 对外路由集中在 api/routes，通过现有服务或能力公开入口完成操作 |
| agent | AI Agent 自身的 skills、prompts、tools、routing/context 及智能体编排 | 模型任务策略与上下文在此维护，普通接口共用的业务和基础服务按其职责归属 |
| capabilities | 按能力或业务域维护规则、校验、公开能力及专属接入 | 可同时服务智能体和普通接口。Agent 的营销接入与 Marketing 的领域业务分别归所属工程 |
| core | 配置、身份、安全、错误定义及日志等基础规则 | 不依赖具体智能体、业务流程、数据库实现或 HTTP 路由 |
| db | MySQL／Redis 连接、数据读写、事务与持久化约束 | 保留原子性和执行资格校验，不反向调用服务、能力或路由 |
| services | 执行协调及附件、记忆、语音、模型通信等实际基础服务 | 按已有职责组织，智能体如何使用这些服务的策略归 agent |
| schemas | 输入输出定义、协议加载与校验、同源生成产物 | 公开类型和运行校验继续从所属 contracts 生成，数据库建表语句归 db 或部署 sql |
| utils | 多个模块确实共用、没有网络／数据库副作用的纯函数 | 单一能力的辅助函数留在原模块，不容纳认证、客户端、查询、匹配或运行流程 |

`agent/` 按实际需要组织自身的 Skill、提示词、工具、路由、上下文及编排，后续新增智能体模块也按此职责归属。模型供应商的技术客户端继续归 `services/clients/`。能力专属的工具声明、协议适配和来源规则按下文随能力维护，由 agent 取得已装配的声明与公开接口。

`services` 中的 `execution` 负责受理、领取、租约、暂停恢复、取消及资源收尾等通用执行协调。`clients` 负责供应商技术请求、响应与连接生命周期。`attachments`、`memory`、`speech` 等保留各自实际服务职责，同一功能的 HTTP、持久化和协议实现分别归 api、db、schemas。通用 memory 的读写、权限和事务沿这些边界维护，只有智能体使用记忆的策略或编排归 agent。

Agent 的 `capabilities/<助手名>` 维护该助手的能力说明、工具声明、显式入口映射、已有资料交接、协议校验及专属通信。`capabilities/marketing` 对接营销助手，订单、拜访等业务处理归 Marketing 工程。附件上传、原件读取、校验与解析准备继续由 Agent 的既有服务提供。

Marketing 的 `capabilities/<业务域>` 维护订单、拜访、客户等领域规则与校验，向智能体和普通接口提供实际需要的公开能力。Marketing 智能体自身的任务 Skill、提示词、工具选择、上下文及跨能力编排归顶层 `agent/`，由其调用所属领域能力。名称包含 AI 或 memory 不决定普通接口共用模块的归属。

小模块先使用单个文件，有可独立维护的职责再拆目录。助手或能力在真实接入时增加，不预建空模块、占位目录或备用入口。目录迁移不引入动态插件框架、自动业务查询或历史兼容壳。

提供内容以当前授权和已有来源为界。转交原消息、附件解析正文、来源、相关历史及调用方已准备的资料，不补造业务事实或增加业务数据获取服务。记忆内容使用所属领域的同源契约校验，如何解释、匹配和采用由领域负责。公共 Schema 与生成产物仍归 schemas，不在 agent 或 capabilities 手写同义 DTO。

应用入口用明确对象或映射装配已接入助手及能力，交给路由与执行层使用。新增助手同步实际接入、装配、契约、配置和测试，保留身份、输入版本、取消、迟到结果、许可及用量规则。目录命名变化不扩大服务业务职责，也不增加模型调用。

环境配置沿用所属工程分层。Agent 与 Marketing 联合部署时，共享模型配置与服务间密钥由 Agent 根配置提供，认证、数据库、服务地址和运行限制等专有项归各服务配置。环境变体保持基础配置的目录层级。


## 3. 公共入口与依赖

应用／进程入口组装具体依赖，管理启动和关闭。agent 使用能力公开入口及实际所需的基础服务。通用执行通过装配后的对象调用智能体或助手，不读取其私有策略与状态。普通接口可通过既有服务或公开能力完成自身业务，无需经过智能体。

capabilities 使用 core、schemas、utils，Agent 的助手接入还可复用 services/clients 的纯技术通信，调用方按权限交接资料。能力不依赖 api、db、agent、services/execution 或其他领域能力的私有实现。db 不依赖 api、agent、services 或 capabilities。core、schemas、utils 不反向依赖上层，utils 不依赖项目其他层。schemas 可使用 core 的错误定义及 utils 的纯函数，core 不反向加载 schemas。services/clients 不依赖智能体、领域能力或执行状态。

同一能力内部使用明确的具体模块，跨能力通过实际需要的稳定公共入口。`__init__.py` 只导出需要的接口，不创建连接、运行任务或安装路由。迁移后清理已无消费者的旧路径，必要的数据与兼容依据按所属契约处理。

普通后端函数不会因为位于 tools 就自动成为模型工具。模型工具具备明确声明、参数校验和执行适配，运行代码继续核对授权、来源和结果。Agent 的助手接入可校验协议和交接结果，业务理解、匹配、完成判定及最终写入仍由原负责方承接。

消费者通过参数提供外部依赖，测试替换相同边界。上述分层说明职责与依赖方向，现有公开入口足够时直接使用，不为目录形式增加转发函数、同义类型或注册机制。
