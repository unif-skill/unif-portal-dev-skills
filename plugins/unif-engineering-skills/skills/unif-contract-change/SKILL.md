# Unif 跨仓契约变更

先确定这次改动影响哪一种数据。字段可能只用于模型输入，也可能被服务转交、业务客户端编辑，或在重启后用于恢复草稿。同一个字段名要沿实际读写路径判断。

职责转移时，从工程 `AGENTS.md` 确认采用的架构修订，沿[架构状态表](https://github.com/unif-design/unif-platform-architecture/blob/main/STATUS.md)找到所属领域的现行契约。架构仓维护跨仓分工与判定条件。对受影响的 Agent、Marketing 或 Portal，从各仓 `docs/README.md` 打开模块说明和实现入口，核对谁产生输入、谁作判断、谁采用结果。各工程按实际接线维护自己的说明和验证依据。

## 找到唯一源和需要更新的产物

定位所属 `contracts` 单元、生成命令和消费者锁定的版本。基础封套和身份归平台基础契约，营销输入、结果和模型投影归 Marketing，Agent API 组合所采用的公开契约。根据字段的实际用途核对 OpenAPI、Python 运行校验和 TypeScript／Go 产物，沿调用方锁定的版本检查读取与写入。[跨工程契约交付](https://github.com/unif-design/unif-platform-architecture/blob/main/runtime/contract-delivery.md)

| 本次任务 | 如何核对源和产物 |
|---|---|
| 实施已定变更 | 修改唯一源，运行生成命令和一致性检查，再按实际依赖更新消费者。 |
| 只读审查 | 对照源定义与各仓差异，核对生成物和消费方锁定的修订。写明漏改的位置及可观察的影响。 |

从一份实际输入或结果往下追，核对谁生产、谁转交、谁保存，以及谁最终读回它。例如，字段已从模型投影移除时，仍要检查 Agent 保存的公开结果和 Portal 冷启动时读取的草稿。

## 判断旧字段何时可以退役

1. 查找仍会读回旧数据的入口，包括旧客户端、队列重放、历史结果和本地草稿恢复。
2. 按已确认的策略迁移有效消费者，验证其原有行为。如果某条旧数据的处置方式待定，列出读取入口和受影响行为，继续已明确的部分。
3. 消费者已迁移并通过验证后，移除退役的生成物、专属测试和文档。

涉及服务端表结构时，把新库初始化和既有数据库分开核实。前者要同步检查建表源、部署 SQL、生成入口及结构测试。后者按明确的数据处置授权迁移或删除历史记录。

## 从消费结果验证契约

验收时用代表性输入核对生成结果，再让有效数据经过运行校验、导入、转交和实际使用，确认无效输入会被拒绝。涉及旧数据时，分别从原有记录和新写入的记录执行恢复。审查已有证据时，说明它覆盖了哪个版本和哪段链路，列出仍缺的采用或运行记录。实施结果按工程已有状态表规则登记。

采用、取消与业务回执查 `$unif-platform-rules` 的 `references/architecture/contracts.md`。业务身份查同一技能的 `references/architecture/state.md`。

| 当前任务 | 方法入口 |
|---|---|
| 审查改动及跨仓影响 | `uni-code-review` |
| 设计有效输入、拒绝及旧数据恢复用例 | `uni-test-design` |
| 选择并运行验收检查 | `uni-verify-change` |
