## 7. 独立开发与验证

### 7.1 依赖治理

涉及第三方库、框架或 SDK 的设计、接入与封装，先按项目采用版本核对官方推荐用法、最佳实践和限制，结合有效契约与实际消费者确定方案；排障先确认官方说明、修复是否已发布及适用性，再选择配置、升级或自有修复。保留关键来源、适用版本与项目验证依据，官方建议不改变已确认的项目选型、行为或授权。详细核查可选用已安装的 `uni-third-party-integration`，不是采用本规范的前置条件。

基本依赖关系为：

```text
交互入口 → 场景组合 → 独立功能 → 外部适配
```

应用组装代码提供具体依赖。功能不反向依赖页面、聊天展示或场景内部状态；跨功能协作优先放在组合代码中。

平台公共能力不反向依赖某个领域的私有实现。跨领域协作通过明确的公开契约与组合代码完成，不穿透领域内部状态；真实复用需求出现时，再评估是否提取公共能力及其维护成本。

公共契约保持精简，只共享具有稳定共同语义的内容。草稿和业务进度留在所属场景，不汇入一个覆盖所有任务的公共状态对象。

设计和开发前，沿本次实际入口查找已有能力、状态所有者和消费者，同时核对已采用库的公开接口。不能只搜索同名文件，也不能仅凭旧方案或目录骨架认定能力存在或缺失；已有公开契约足以核实的部分不要求遍历提供方内部实现。

已有能力满足需求时直接复用，职责一致且能合理补足时在所属实现扩展；无法合理满足时才在授权内替换或新增，并说明具体缺口和影响。新需求不要求旧代码已经实现，但不能跳过相关能力核查，按文档章节或入口名称另建同职责流程、管理器或状态副本。

同一运行工程内同一职责保持一套有效实现，各入口保留自己的参数、交互和业务差异。替换后迁移实际消费者，清理已失效且确认无消费者的实现、类型、配置和测试；有真实数据、消费者或兼容依据的内容按所属契约保留。不同实例的状态与生命周期不因复用代码而合并。

已明确采用不同语言的独立客户端，各自维护必要接入代码，共用所属业务服务和同源契约，并验证相同语义；不要求为复用增加跨语言执行层。最终业务规则和事务仍由业务系统负责。

同一产品的 RN 与原生鸿蒙客户端按共同需求和行为案例持续对齐；可以先完成一端再实现对应端，分别登记采用契约、修订、平台差异和验收证据。平台专属需求及局部修复按授权限定，不自动扩大另一端改动。能够验证的纯逻辑与资源保持同源；React／ArkUI 展示和平台资源接入各自实现，不以包名对应推断实现或运行兼容。

使用类型检查、导入约束、静态引用分析和现有测试工具识别消费者。任务指令引用、跨系统契约和 H5 协议等静态 import 不能完整覆盖的关系，补充少量明确的对应关系，服务于检查和测试选择。

契约变化时，识别生产方、消费者和相关组合链路，验证结构与语义影响。跨部署版本的兼容范围由实际发布约束确定，不默认为各端同时升级。

公用记忆模块维护自己的可执行公共契约、服务实现及按需生成的类型和薄客户端，当前宿主与工程组织以记忆架构（规范源相对路径：`capabilities/memory.md`）为源，各消费仓库锁定所用版本。消费者契约验证补充跨仓依赖关系；不直接导入其他仓库私有源码、共写记忆数据表或复制手写 Schema。领域内容契约的归属与公共接口分开，按记忆文档约定协作。

### 7.2 测试责任

| 验证范围 | 证明内容 |
|---|---|
| 单功能验证 | 真实功能在替代外部依赖下的输入输出、错误及副作用 |
| 场景组合验证 | 准备、选择、确认、调用顺序和结果处理 |
| 入口与接线验证 | 页面和聊天进入同一链路，真实依赖已经接入 |
| 模型任务评测 | 意图理解、参数提取、澄清、任务切换及类型化输出 |
| 集成与业务系统验证 | Portal 验证实际请求响应、权限、码表及接口承诺的业务结果；业务系统验证内部规则、事务与持久化 |
| 真机验证 | 设备权限、原生宿主、设备操作及产物生命周期 |

测试真实被测功能，替换网络、设备等外部边界。替身须符合所用依赖的接口、参数和前置条件。结果取决于依赖自身行为时，用该版本的真实实现另行验证。断言返回和状态，也断言不应发生的提交或其他副作用。异步请求、身份或资源会在等待期间变化时，按契约区分保持结果有效的更新与使旧操作失效的转换，让真实实现及消费者经历这些变化；标识再次出现不单独证明仍属于原操作。模拟模型输出不能证明理解准确，结构校验不能证明业务成功。

测试质量以真实行为断言为依据。迁移或合并测试时，按当前契约保留仍有效的行为保护、替换失效断言；共享单元的新增测试不代替尚未覆盖的消费者接线与副作用验证。覆盖报告纳入本次验收的源码，不以排除有效文件或削弱断言凑指标；预期来自契约，不复制实现算法。用例数据和资源隔离，等待异步工作及清理完成，并采用工程的测试超时约束。不稳定用例保留首次失败，重试通过不等于问题修复。

本地快速验证按影响范围执行。系统合并和发布按实际 CI 配置完成 required 验证，定向测试不能替代完整门禁；同一验证阶段避免重复执行相同测试。

### 7.2.1 日志与故障诊断

Unif 各运行工程采用通用[错误与诊断原则](https://github.com/unif-skill/uni-skills/blob/main/skills/uni-code-organization/references/functions-and-async.md#错误与诊断)，本节维护公共接入、字段、附日志与验收约定，并作为阶段技能的同步来源。日志责任随功能开发、修改、重构和审查一并落实；SDK 专项文档只说明采用版本的具体接口。

验收目标是一次问题发生后，能用当时已有记录串起原请求、关键阶段、失败判断和可取得的原因；不能以再次复现并临时加日志作为常规前提。外部调用、模型与协议转换或校验、持久化、异步交接、降级恢复需有对应证据。纯取值、样式、渲染和正常预期分支不机械新增日志；业务结果和技术异常按契约区分。主日志、链路关联与分类附日志按以下条件选用，不要求每个功能或改动产生三份记录；开发任务未提“日志”也须检查本次实际涉及的责任边界。

**主日志。** 统一入口提供时间、级别、稳定的应用标识、模块和事件，以及操作关联、阶段、结果和安全原因。可读格式为 `UTC时间 LEVEL [应用] [模块] 事件 key=value`，应用标识如 `unif-portal`、`unif-agent`、`unif-marketing`；结构化字段保留独立语义，业务代码不拼前缀或另造打印通道。事件名稳定，不嵌入用户内容或动态 ID。外部请求记录安全状态与耗时；转换、校验或丢弃结果记录规则／契约、字段或项目位置、具体受控原因及采用结果，不能只剩“失败”“无匹配”或通用包装码。大内容按下述附日志交接，不塞入主行。

级别按实际影响选择：`ERROR` 表示无法继续的技术／契约故障或关键状态失败；`WARN` 表示需关注的依赖失败、降级或可恢复异常；`INFO` 表示关键步骤、已取得事实和状态恢复；`DEBUG` 表示按策略保留的高频排查细节。正常取消、合法无匹配和需要用户补充不默认记为错误。最有上下文的一层记录完整安全原因，其他层只补新增决策与关联；去重或采样仍保留原因变化和恢复。调整展示格式不顺带改变级别、采样、过滤或恢复策略。

日志调用点与异常起点分开：`log_source`／`log_function` 定位记录位置，`error_source`／`error_function` 定位可确认的故障来源。位置从运行时或已有异常栈提取，只保留安全的相对源码路径或文件名及有效行列；不手写行号，不把包装层当根因，不从任意异常文字猜来源。无法可靠取得时省略，压缩产物结合对应版本 sourcemap；客户端 Info／Debug 不另建定位栈。安全诊断保留错误类别、原始码及必要原因链，无法取得的原因明确未知。

**链路关联。** 原请求／轮次、内部操作和父子调用使用各工程已有的安全关联字段，在操作开始时固定，并贯穿 HTTP、模型调用、队列／任务、持久化和异步收尾。跨工程交接传递受控关联或明确的映射，不以整份上下文传播身份凭据；新重试与原请求的关系可追溯。用户身份、实例、操作和运行期分别校验，迟到结果或清理留在原操作，不能因记录时读取当前状态而混入新身份。准备、已交付、已接收、已持久化和业务确认分别记录，传输成功不替代业务成功。

**分类附日志。** 模型输入／输出、大响应、解析结果或校验上下文影响定位且超出主日志容量时，按工程已声明的类别和采集策略启用受控附日志。该策略在执行前确定；必要失败上下文不能仅因其体积大而丢失。复用所属公共日志组件和文件治理，不由每个业务模块自行建目录、写文件或创建另一套生命周期。

主日志保存与原操作关联的索引：类别、受控句柄或相对引用、状态、大小及必要的摘要，按实现补充校验信息；不暴露绝对路径、任意外部 URL 或正文。附日志保留诊断所需上下文及规则／格式版本，并明确截断、脱敏、采样和未采集状态；关闭、过大或写入失败也要有可识别的受控原因，不能生成看似可读的空引用。普通业务字段优先投影，只在定位确需且满足访问边界时保存更完整内容，禁止无条件转储所有请求或响应。

主日志和附日志都排除密码、密钥、令牌、认证头等凭据；按现有业务与身份边界脱敏，限制单项、队列和总体容量。附日志使用应用／服务私有目录和受控读取，声明身份隔离、权限、保留时间、轮转与清理规则；有读者持有的产物按真实交接结束释放。默认不公开、不上传、不入业务库、不入版本库；导出与分享按明确授权和现有资源契约执行。日志与附日志治理参数由宿主统一持有，不能用临时调试开关撤掉原有保护。

**故障与验证。** 日志入口、附日志写入、索引生成或清理失败不得改变业务返回、异常传播、权限、事务、资源归属、重试、恢复或用户提示；记录安全的健康状态或保存失败原因，不递归写入已经失败的通道。测试从一次受控失败产生的真实记录检查阶段、原关联、具体安全原因、级别、脱敏和必要附日志的可读取性，并覆盖取消、迟到、身份切换、容量／截断和诊断存储失败等实际边界。格式或定位变化另核对记录点与异常源、来源不可用和重复记录。不能只断言 logger 被调用或界面出现提示。

审查沿失败产生、转换、抑制、降级和交付核对证据是否足够；缺少根因时说明缺口，不把通用码或猜测写成结论。必要历史只解释当时事实，不代表业务成功，也不替代权威业务状态。分别报告规则／源码、自动化记录、真实存储、运行环境和业务证据；本节的规则完成不代表各客户端、服务和 SDK 已全部接入。

### 7.3 变更影响

| 变化 | 验证范围 |
|---|---|
| 后端字段或响应包装变化，业务语义不变 | 原始协议校验、适配映射测试及必要联调；确认仍产出相同功能契约，不要求所有页面改动 |
| 功能内部变化 | 本功能及实际受影响的适配、消费者和组合 |
| 单个任务指令变化 | 该任务评测，必要的识别、切换和复合意图样本 |
| 共享契约或通用指令变化 | 受影响的生产方、消费者、任务和场景 |
| 共享状态变化 | 相关读写者、任务切换及异步结果交接 |
| 记忆公共接口、权限或生命周期变化 | 实际调用方的契约与相关组合；检索结果或装配语义受影响时补对应任务评测 |
| 设备适配变化 | 设备功能、相关场景和 H5 消费者；涉及原生行为时补真机验证 |

影响范围无法完整确定时，扩大到相关领域及集成链路，并补齐遗漏的依赖关系。完整验证发现的漏测问题用于修正定向选择规则。

### 7.4 设计交付的最小依据

设计说明按本次变化提供可检查的依据，不规定固定目录、文件模板或每函数一份文档：

- 能力、场景和入口各自承担什么，哪些处理仍为内部普通函数；职责调整后，原有已确认能力与业务行为由谁承接、通过什么接口衔接并验证；每个额外字段、状态、交互或调用对应哪个已确认需要和实际消费者。
- 涉及新增、替换或共享能力调整时，简短列明已有入口、实际缺口和处理方式；复用部分与需要修改的部分分别可定位，不只写“复用现有能力”。
- 场景每一步由谁触发、通过哪些已有参数、props、ref 或事件回调进入哪个功能；输入由谁准备，前一步输出如何交给下一步，结果如何回到展示。公共组件与所属业务场景之间的交接必须具体，不能只写“由 Portal／调用方处理”。已有接口足以承接时直接引用，不另建同义接口；已有数据的复用、刷新和后续调用归属明确，不能为定位既有业务目标而额外发起未授权的创建、提交或状态更新。
- 各结果状态能否由真实数据构造，接收者如何处理；文字描述、类型的必填／可选约束与验收样本必须一致。用于展示的空值不能补成业务身份或已满足的条件。
- 写明所属业务场景或应用功能，由它维护草稿、确认、请求与结果采用，公共展示组件只接收必要数据并交付事件；最终业务事实由所属业务系统处理与保存，取消和迟到结果仍有原归属。普通调用可由参数、返回值和局部状态完成时，不额外要求公共关联标识或运行机制。
- 外部依赖如何替换、谁实际消费该契约、优先验证哪些行为，以及什么变化需要扩大验证。

已有契约覆盖且公共语义不变的内部调整，引用对应依据和已有验证即可，不重复设计完整模块。设计定义验收范围，交付时提供实际执行证据；类型示例通过检查不能代替场景交接和业务语义审查。

纯能力按本次明确的输入输出及副作用完成设计，不需要预先穷举所有使用场景；本次范围包含交互或场景组合时，必须补齐该段事件、确认、调用和结果交接。尚待设计的其他流程在 STATUS.md 限定范围，不能以基础能力已完成代替完整场景已完成，也不由开发者补猜默认流程。
