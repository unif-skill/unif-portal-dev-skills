# Portal 文件开发规则

本文维护 Portal 客户端对通用工程规范的采用方式及项目专属约定。代码组织、RN 实现和技术文档遵循目标工程已采用的规范，来源由工程入口指明。目录归属见[工程组织](../../SKILL.md)，能力边界见基础能力架构（规范源相对路径：`capabilities/portal-foundation.md`），业务契约与状态原则见平台架构（规范源相对路径：`ARCHITECTURE.md`）。

本文是 React Native 客户端工程规则。原生 ArkTS／ArkUI 应用与库使用鸿蒙开发规则（规范源相对路径：`HARMONY_DEVELOPMENT.md`）和鸿蒙工程组织（规范源相对路径：`HARMONY_STRUCTURE.md`）；不把 TypeScript 文件名或 React Native 目录套用到这些工程或 Agent、Channel、CLI 的其他语言实现。新 Portal 按[平台架构第 1.1 节](../common/scope.md#11-设计依据与适用范围)重写；旧源码用于核对行为与逻辑结果，不作为文件搬运来源。新工程已有代码的日常修改仍限定在本次功能及实际影响范围内，不自动全仓重排。


## 1. 文件变更入口

在 Portal 客户端开发、测试、审查或交付源码及配套文件时，按工程入口取得已采用的通用规范及本次相关的 Portal 约定。新模块、公共契约、状态归属或场景职责需要设计时，取得相应设计依据；已有契约下的内部等价修改不重复开展完整架构设计。技能按已安装目录中的适用描述选择，不以另一技能的安装位置作为规范来源。

开发前定位本次功能契约、所属单元、已有公开入口、实际消费者和对应测试。新增文件落在已确定的单元中；新增单元时说明其独立职责和使用方，不从页面名称或 SDK 包名直接推导一套业务模块。

工程提供设计与开发状态表时，先核对本次条目的范围、设计依据、所需技能或规范、执行归属及具体限制，再读取对应契约。设计完成不等于代码已实现或已验收；未核对不等于未开始。状态表只作范围与依据索引，不替代契约正文、当前任务授权或真实验证证据。

设计已完成且本次必要规范实际可用时，在已授权范围内直接开展工作；局部未决项只限制依赖它的部分，已有契约下的内部等价调整不重新设计。记录与已明确的最新依据不一致时核对并更新，不因登记滞后重做已有成果。目标工程应明确资料的可访问位置或版本，安装技能不表示项目状态与模块契约已经同步。

用户已明确的需求和契约限定实现范围。重写实现和后续文件组织调整不增加重试、自动提交、缓存、恢复、确认或新接口调用。


## 2. 各类代码的开发规则

Portal 具体归属见[工程组织](../../SKILL.md)。在工程已采用的职责与依赖规则上补充以下项目约定：

| 单元 | Portal 约定 |
|---|---|
| components | 优先使用 Design、Chat 及当前工程共用组件；确认 UI 的采用结果由所属场景处理 |
| capabilities | 按所属能力契约接入 SDK，保留调用、取消、资源和平台责任 |
| domains | 页面和对话复用所属领域链路；最终业务规则与事实由业务系统处理 |
| integrations | 按所属协议及真实接口码表转换 DTO、请求和结果，不补造身份或业务成功 |
| app | 账号、设置、对话各自维护状态；bootstrap 与导航负责真实组装 |
| hooks、utils、config、types | 采用通用文件规则；Portal 配置、业务存储和资源的具体归属见工程组织第 3 节 |

测试、脚本与原生配置沿用实际工程工具，不套用手工 TypeScript 单元的文件名。
