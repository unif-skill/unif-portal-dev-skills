# 新库接入与首次／恢复发布

本专题用于 @unif React Native 库的新建、工程标准接入和首次／恢复发布。原生鸿蒙 HAR 库从[鸿蒙适用范围](harmony-scope.md)取得依据，按其实际标准处理 OHPM 产物，不套用下文 npm 模板。普通组件修改、已成熟工程的日常维护和单纯版本查询不因此启动接入、建站或远端配置。

## 标准来源与实际接线

以下路径相对于组织标准仓 `unif-design/.github`，不是平台架构仓。优先采用任务或工程明确的来源／修订；未指定时先核对组织默认分支的已提交标准，工作分支差异和未提交草稿另行识别，不把本机文件存在当作已采用依据。

| 当前需要 | 按需读取的标准源 |
|---|---|
| 新仓接入顺序、实际前置条件 | `ONBOARDING.md` |
| 工程文件的模板、覆盖范围与同步行为 | `docs/13-sync.md`、相关 `templates/` 文件和 `scripts/sync-repo.sh` |
| PR、必需检查与远端仓库设置 | `docs/05-branch-protection.md`、`scripts/setup-repo.sh` 及其引用配置 |
| 自动版本、标签、Release 与机器人发布 | `docs/04-release.md`、`templates/workflows/release.yml` |

对照本库 manifest、脚本、workflow 和真实消费者确认哪些已接入、哪些仍是脚手架；缺少实例时定向查看已采用相同标准的 Design 等库，实例不能代替标准源。组件职责和接口继续采用所属架构契约，不为工程接入扩读全部领域资料。

同步脚本会修改目标文件，设置脚本会改变远端；执行前核对实际影响与授权，不能把“同步”或“幂等”当作只读操作。依据模板差异调整需要的接线，不以脚本退出成功认定所有标准已接入。规范修订或模板与任务采用依据存在冲突时，指出位置和影响，继续不依赖该差异的已授权工作；模板行为及回归由组织标准源维护，不在技能中再实现一套。

## 首次与恢复发布

先确认包名、scope、目标 registry、仓库身份及历史版本／标签／发布记录。注册表查询失败、404 或空列表只说明这次没有取得相应信息，不证明版本从未占用；已有发布记录的版本不能因当前不可见而当作新版本重发。按完整历史和组织版本规则确定后续候选，不通过试发或覆盖标签探测可用性。

采用组织规定的 PR、必需检查和机器人发布链路：npm 发布使用既定 OIDC／Trusted Publisher，版本、标签和 Release 由规定的自动化处理。具体触发条件、配置与凭据分工读取发布标准，不沿用脚手架 release 命令或因个人账号有权限就改成本机发布。

核对实际远端的保护与必需检查、发布机器人对目标仓的访问和受保护分支接线、Trusted Publisher 的包／仓库／workflow 绑定及发布配置。模板存在或 CI 一次通过不证明这些前置均已完成。缺少条件时列出差异及相应配置／验证责任，保持既定发布方式；真正首次包的引导方式若尚未有明确依据，先说明缺口，不自行创建临时发布或凭据流程。

本地实现与模板差异核对、提交／合并、远端设置、CI 触发／重跑和实际发布按各自授权推进。合并若会触发发布，需把该后果纳入交付范围；发布前置未齐不阻断可独立完成的本地功能，但不能宣称已具备发布条件。
