# React Native 库开发

维护 @unif 库源码、公开类型、依赖、原生接线、示例或发布产物时读取。应用仅使用库的公开 API 时，读取对应组件或能力契约即可。

## 依据与单元

从当前库的工程入口、package.json、公开出口及本次单元的类型、实现和测试取得依据。任务指定的新架构定义目标职责，当前代码和已采用版本定义已可用接口；设计完成不表示 npm 包已经实现或发布这些接口。

Design 的设计入口是 `libraries/react-native-design.md`，Chat 是 `libraries/react-native-chat.md`；其他库采用其所属契约，不从包名推导一套实现。库文件遵循自身构建与原生工具约定，不套用 Portal 的 app、domains、capabilities 目录。

公开单元可以独立理解、消费和验证。真正共享的实现放在有明确使用者的内部单元，通过小型入口复用；内部支撑不因被多个组件使用就进入 npm 公共 API。库不依赖 Portal 的路由、业务 store、私有 DTO 或日志实例。

## 变更与联动

- 公共输入、事件、默认值、错误、资源和平台支持以所属契约为准。已有公开类型从唯一代码源导出，消费者和示例不各自手写同义结构；目标接口尚未实现时按本次授权实现，不能在应用接入中假装当前依赖已支持。
- 公开接口或行为变化时，核对源代码出口、类型产物、文档生成、实际示例及消费者。仅整理内部文件不扩大公共表面；组件文档、Website 和 llms 资料按库已有生成链维护。
- 依赖变化按当前 manifest、锁文件、实际安装和库内依赖检查确定范围；example、Website 或消费者实际采用不同版本时分别核对。历史 peer 范围、例外和脚本名称不作为所有库的固定要求。
- 只改本次单元及真实受影响的共享部分。组件调整不要求先重排全库、统一所有主题状态或创建跨库运行框架。

## 验证与交付

从实际公开入口验证本单元行为，再按公共类型、主题、共享实现、平台适配和依赖变化找消费者；组件通过 props 或内容组合形成的关系也要核对。外部依赖可替换，但被测组件、映射与状态交接使用真实实现。

类型／逻辑、组件交互、example／消费接线、打包、原生／Web 与设备验证分别提供证据。测试替身不能证明宿主、布局或设备能力；库单测不能证明 Portal 已接入，设计文档不能证明库已发布。

检查命令、执行环境、版本与发布方式取本库当前约定，完整 CI 核对本次提交。本文提供库规范，不因读取它再次启动测试、审查或交付；这些工作按当前任务的实际阶段和授权进行。
