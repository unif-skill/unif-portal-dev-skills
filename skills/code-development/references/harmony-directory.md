# Unif 原生鸿蒙工程组织

本文定义 ArkTS／ArkUI 应用、原生库和共享资源的职责归属。文件、状态与验证规则见[鸿蒙开发规则](../SKILL.md)，系统职责见平台架构（规范源相对路径：`ARCHITECTURE.md`）。目录用于真实职责，不是必须预建的文件清单。


## 1. 工程目录与依赖

应用沿用 Stage 工程与实际模块配置；在所属模块的 `src/main/ets/` 下按需要组织：

| 单元 | 责任与依赖 |
|---|---|
| `app/` | 启动、导航、依赖组装及账号、设置、聊天等应用功能；各功能维护自己的状态 |
| `components/` | 跨功能的展示与交互；消费输入、事件和主题，不直接读取业务状态或发请求 |
| `capabilities/` | 设备与本地操作、取消和资源交接；优先消费已有库公开能力 |
| `domains/` | 所属业务功能、准备／确认／提交及场景组合，复用当前业务契约 |
| `integrations/` | HTTP／SSE／H5 等外部协议、DTO 与转换；不决定额外业务流程 |
| 平台配置、资源、测试 | 采用工程实际的 `resources/`、测试源集、包清单及构建路径，不搬用 RN 目录模板 |

应用入口只做实际组装，下层不反向依赖入口或全应用状态对象。新增单元按已有契约与消费者归属，不把 SDK 名称或页面名称自动变成业务模块。

`@unif/harmony-*` 采用独立 HAR 工程／模块和自身公开入口。Icons 负责图标，Design 负责主题及通用 UI，Chat 负责聊天呈现组合；Camera、Scan、Umeng 负责各自能力和必要 UI。应用账号、业务请求、草稿和上传流程不搬入库，库不依赖 Portal 私有代码。具体包是否存在、互相依赖哪些组件，以当前工程核实。

库的示例应用通过公开包入口消费，构建配置明确区分 HAR 与应用宿主。源码模块路径和发布包两种消费方式分别核对；本地构建通过后仍需检查可分发产物中的导出、资源与传递依赖，不将作者工作区的路径作为发布依赖。
