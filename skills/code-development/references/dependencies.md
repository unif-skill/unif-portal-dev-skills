## 4. 公共入口与依赖方向

| 使用方 | 可以依赖的内容 |
|---|---|
| 应用组装与导航注册 | 各功能的公开接口、必要宿主、配置与具体适配实现 |
| 页面、对话等入口 | 所属场景或查询功能、展示组件及必要的输入转换 |
| 场景组合 | 被组合功能的公开接口，负责步骤、交互和确认 |
| 独立功能 | 自己的契约、普通辅助函数，以及显式提供或正常导入的必要公共依赖 |
| 通用组件和 hook | 组件库、React 与必要 UI 依赖、其他公开 UI 单元、通用辅助及必要日志接口；不读取应用或领域业务状态 |
| 基础能力、外部适配 | 对应 SDK、协议代码和必要公共支撑能力；不反向依赖页面或具体业务场景 |
| 通用工具 | 与用途直接相关的基础计算代码；不依赖组件、应用组装和业务模块 |

模块间使用明确的公开文件或小型 `index.ts`。不建立导出全部组件、工具、领域或设备能力的总 barrel；使用一个基础组件不应因此加载全部业务代码。内部文件可以按普通相对路径协作，不对外导出私有辅助实现。

日志的常规调用与全局捕获安装、文件存取分别提供必要入口，组件使用日志只依赖常规调用入口。

同一层的两个单元可以通过公开接口形成必要、无循环的依赖，例如 Sheet 使用键盘 UI 单元。公共功能按实际职责和消费者确定归属：领域内共用的查询仍留在所属领域，跨领域通用的设备操作归基础能力，不因多处使用就移入全局组件或工具层。两个业务功能共同完成场景时，把协调留给场景，不相互驱动对方的状态。

`import type` 仍算依赖。通用组件不能通过导入领域私有类型取得业务状态结构；需要的展示类型由组件定义，入口完成必要投影。确有共同语义的公开契约可从拥有它的功能引用，不因相似字段就新增全局类型仓库。

需要身份、HTTP 客户端或原生依赖的功能，通过普通参数、小型依赖对象或所属适配器接入。应用组装连接真实实现；不要求通用依赖注入容器、事件总线、能力注册中心或运行时插件框架。

工程开始接线时，`AGENTS.md`、路径别名及导入检查同步采用本目录规则。优先使用现有 TypeScript、ESLint 导入约束和静态引用工具检查跨界、私有深路径与循环依赖；工具配置维护可执行规则，文档解释职责。不复制另一套按旧模式目录或固定文件模板判断合法性的规则。


## 5. 基础能力与资源归属

拍摄与媒体选择、定位与地点查询、地图与选点、SQLite 与文件存取、扫码、蓝牙、分享、语音及系统支撑的完整职责、组合和消费者在Portal 基础能力架构（规范源相对路径：`capabilities/portal-foundation.md`）维护。某项能力分散在旧页面、工具或业务目录中时，也按完整调用链纳入，不只盘点同名文件夹。

每项现有用途都要明确是独立能力、客户端组合、交互入口、领域适配还是未接入占位。普通功能与复杂组合可以在同一模块内分别验证；SDK 全集不等于产品需求，已有组合也不能因职责拆分而丢失。

平台相关实现留在对应能力或 UI 单元内部。继续被 Web 预览使用的代码应有实际可用的 Web 实现或明确表达支持范围的适配，不以成功替身假装设备操作已经完成；测试替身与正式平台实现分开。原生配置和依赖变动通过真实构建与设备验证确认。
