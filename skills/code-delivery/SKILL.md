# 代码交付

以任务授权的交付阶段为终点，保证变更范围、验证对象和远端结果一致。

## 工程依据

核对仓库、远端、当前分支、工作区与暂存状态，以及任务要求的目标分支和交付阶段。读取工程的 AGENTS.md、贡献约定、检查脚本与 CI，采用其中的分支、提交、合并和版本规则。GitLab 优先使用 glab，GitHub 优先使用 gh，本地版本操作使用 git。

实现与审查采用工程指定的架构和契约；门禁以当前工程配置为准。跨仓公共契约变化核对实际消费者和发布兼容条件，不预设各仓同时升级。

## 组织与验证

按用户指定的分支方式工作；未指定时在写入前使用独立功能分支，并行任务隔离工作树。已有混合改动只承接明确属于本任务的部分，保留他人的工作、暂存内容与占用中的工作树。

提交围绕可独立理解和验证的变更组织，检查实际暂存差异及新增文件，不把整个脏工作区当作本次提交。标题和正文按工程约定说明最终行为及原因。

本地按实际影响验证；系统合并和发布完成工程规定的门禁。已有检查仍覆盖相同内容与环境时复用证据，代码、依赖或检查对象变化后补充相应验证。需要代码审查时使用 code-review，或按工程的审查要求执行；定向测试不能代替完整门禁。

## 远端交付

沿已授权阶段连续执行，不重复询问相同许可；本地提交、推送、创建 PR/MR、合并和发布分别核对是否在授权范围内。额外授权缺失时，先完成可以独立交付的准备并说明剩余动作。

推送后核对远端与 PR/MR 的实际提交；合并前确认最新 head 的审查和 required 检查成立，不能使用旧提交的绿色结果。合并后核对目标分支及工程要求的后续 CI。版本、tag 和 Release 按该仓发布规则处理，不从“提交”或“合并”自行推导发版。

清理先核对分支 tip、独有改动、未提交文件和工作树占用。普通合并用祖先关系确认；squash 或 rebase 合并需核对对应合并记录与补丁或内容等价证据。只删除已确认交付的分支，并在远端删除前防止新提交被一并删除。

交付时报告实际完成的阶段、提交或 PR/MR 链接、验证结果及未完成项。未运行、仍在执行和受阻的检查分别说明，不把提交成功等同于合并、发布或安装生效。
