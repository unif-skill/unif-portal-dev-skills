# 审查规范

审查者必须具有本次适用的企业依据。同一上下文已读且仍适用的规则和契约直接复用；独立审查任务需取得自身尚未具有的正文，不能只凭“父任务已读”略过。缺失部分优先从工程指定规范取得，未指定时按以下入口定位：

- 客户端或库的文件、依赖、组件与测试：先确定 RN／原生鸿蒙及应用／HAR／共享核心，通用目录和文件规则从 code-organization 取得，RN 实现和库工程分别按 react-native-development、react-native-library 核对，并按实际变化选择 code-development 的项目与对应平台主题；不将 RN 文件角色、Hooks 或 API 用作 ArkUI 的审查标准。共享源核对生成与真实消费者，语义对齐不要求接口语法相同。
- 模块职责、公共契约、状态与调用交接：architecture-design 的相关主题和目标模块契约；对照既定设计审查不自动变成重新设计。
- Python 后端的文件归属、依赖方向及运行/事务所有权：按变化选择 backend-development 的相关主题。
- 外部依赖、持久化、异常转换、异步收尾、降级或恢复变化：按 architecture-design 的“独立验证”主题逐项检查失败路径的诊断责任和测试证据，确认原因未在包装或抑制时丢失、敏感数据不进入日志、原业务控制保持。
- 对照已确认契约、任务计划、单元与文件组织、实际实现及消费者，区分应同步的设计变化与应修正的实现缺陷；规范版本和契约来源随审查材料提供。

问题应指出违反的规则、代码位置与实际影响；评测样例与通用风格偏好不能成为新增需求。将这些要求用于当前审查，不另起一轮流程或扩大操作授权。
