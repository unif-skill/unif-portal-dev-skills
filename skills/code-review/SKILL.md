# 代码审查

根据实际变更与采用的规范，指出会影响正确性、契约或维护的问题，并给出可复核的证据。

## 范围与依据

确定审查基线和目标版本。审查工作区时同时核对暂存、未暂存和本次新增文件；区分本次改动与他人未完成的工作。作者说明用于定位目标，不替代差异和源码证据。

按工程指定的需求、架构、开发规则和相关模块契约判断。沿公开入口追踪实际消费者、依赖与测试，缺少依据时标明受影响的判断，不把旧实现或其他工程的惯例当作当前要求。

## 核对

- 检查变更后的调用链是否仍满足输入输出、副作用、状态归属和协议语义；公共契约变化同时核对生产方、消费者与实际部署兼容范围。
- 结合实际用途判断文件归属、重复实现、资源生命周期及相关安全或性能问题。已有契约覆盖的等价整理沿用有效设计，不因多处复用就新增全局抽象。
- 检查测试是否执行真实被测实现、覆盖本次行为及受影响交接。已执行的定向检查、完整 CI、构建和设备验证分别记录；测试通过不能替代语义审查。

## 结论

先列有依据的问题：严重程度、文件位置、触发条件和影响，必要时给出最小修正方向。疑问和可选改进与缺陷分开；同一原因不拆成多条，没有发现问题时直接说明，并列出审查范围与证据限制。

审查请求本身只读；修复、提交或向 PR/MR 发布评论按任务授权执行。需要独立审查时，只提供需求、规范、变更范围与原始材料，不传递作者的预期结论。
