# Unif 平台架构

本文只规定各业务领域共同遵循的系统职责、模块边界、契约、状态归属和工程验证原则，供各团队设计自己的领域架构。领域术语、业务功能、场景、具体接口约定和任务专属指令由领域文档维护，本文保留入口引用。

本文描述平台的目标架构。领域与模块设计、实现按可独立验收的业务链路逐步推进，每批明确必要契约和受影响消费者；具体实施批次与接入步骤在实施计划中维护。


## 1. 架构目标

平台通过独立功能和普通代码组合实现业务场景，使功能可以独立开发、组合复用和定向测试。

架构应降低模块之间的耦合、理解和修改一个功能所需的范围、验证变更的耗时，以及开发与业务运行中的模型上下文、调用次数和 Token 消耗。

模块首先是代码和测试边界。功能独立不要求独立部署，也不要求成为独立服务或智能体。新增公共抽象、通用机制或运行边界时，应说明实际问题、受益的消费者及维护成本。

架构成立的判断标准是：

- 修改一个功能，主要理解和修改该功能及必要依赖。
- 更换交互入口，核心功能和调用链路保持一致。
- 新增场景，优先组合已有功能。
- 修改单个任务，可以独立维护和评测，并识别必要的共享影响。
- 验证一个功能，可以替换外部依赖，并找到真正受影响的消费者。
- 确定性工作由代码完成，模型参与必要的理解和推理。
- 业务成功有明确的业务 `code` 依据。

### 1.1 设计依据与适用范围

设计和调整以当前有效需求、契约、实现及实际消费者为依据，先核对已有能力和受影响流程。职责调整须完整承接已确认的能力与业务流程，明确负责方、调用交接和验收依据；由 H5、SDK、业务系统或其他模块负责的部分仍属于完整链路，不能因当前模块不实现而删减能力、业务检查或必要验证。源码、接口和测试用于核实实际输入输出、状态、副作用及外部约束；实现与有效契约不一致时，说明差异和影响，不用现状覆盖契约。参考事实与接入差异按第 9 节维护。

Portal 及 Agent、Channel、CLI 等相关工程基于现有实现和有效契约开发与维护。已有能力满足需求时复用，缺口在所属实现补齐；确需新增、替换或重构时，说明依据与影响，保留未要求改变的行为和契约。已采用的 SDK、组件库及公开类型通过包接口使用。仓库、服务与部署调整按本次需求、实际消费者和已确认的组织方式决定。

开始或接续任务时，核对当前需求、有效契约和已有决定。已排除的需求与已失效的结论不作为实施前提。审查独立核实代码和证据；需要调整已确认范围时，说明新增依据与影响。实现缺陷、设计缺口、待验证项和可选建议分别表达。

本文的“现有业务系统”指承担最终规则、权限、事务和业务事实的系统。经业务方或接口契约确认的外部规则属于接入约束；客户端或中间层已有的处理方式不单独构成业务规则。外部能力不足以满足目标契约时，明确记录缺口及其影响，不由适配器伪造支持。

“代码是事实来源”表示代码证明实际实现，类型、运行时校验和模型 Schema 从可执行契约同源取得；设计中的字段、筛选规则和交互要求仍需业务或职责依据。已确认的新需求不要求当前代码已经实现；源码中的处理也不自动成为新需求。尚无依据的业务规则和外部能力保留为待确认项，不写成有效流程或用默认值补齐。

已授权范围内的内部组织、等价转换和必要验证，可以按工程判断推进。新增或改变用户可见行为、请求次数、副作用、状态归属或业务结果语义，须有已确认需求或契约依据；不能以“更稳健”“顺便完善”为由自行加入产品能力。接入核实围绕当前调用需要的输入、响应、可观察副作用和生命周期交接；已有契约与证据足以确定该交接时，不再要求调用方证明提供方的内部实现。已有契约覆盖的行为直接沿用；确需产品选择时才明确问题及影响，同时推进不依赖该选择的工作。

渐进式推进控制实施和验收范围。临时适配、替换顺序及结束条件由实施计划维护，与功能的长期职责分开。
