## 7. 独立开发与验证

### 7.1 依赖治理

基本依赖关系为：

```text
交互入口 → 场景组合 → 独立功能 → 外部适配
```

应用组装代码提供具体依赖。功能不反向依赖页面、聊天展示或场景内部状态；跨功能协作优先放在组合代码中。

平台公共能力不反向依赖某个领域的私有实现。跨领域协作通过明确的公开契约与组合代码完成，不穿透领域内部状态；真实复用需求出现时，再评估是否提取公共能力及其维护成本。

公共契约保持精简，只共享具有稳定共同语义的内容。草稿和业务进度留在所属场景，不汇入一个覆盖所有任务的公共状态对象。

同一运行工程内优先复用同一功能实现。已明确采用不同语言的独立客户端，各自维护必要接入代码，共用所属业务服务和同源契约，并验证相同语义；这属于契约复用，不宣称共享函数实现，也不要求为复用增加跨语言执行层。最终业务规则和事务仍由业务系统负责。

同一产品的 RN 与原生鸿蒙客户端按共同需求和行为案例持续对齐；可以先完成一端再实现对应端，分别登记采用契约、修订、平台差异和验收证据。平台专属需求及局部修复按授权限定，不自动扩大另一端改动。能够验证的纯逻辑与资源保持同源；React／ArkUI 展示和平台资源接入各自实现，不以包名对应推断实现或运行兼容。

使用类型检查、导入约束、静态引用分析和现有测试工具识别消费者。任务指令引用、跨系统契约和 H5 协议等静态 import 不能完整覆盖的关系，补充少量明确的对应关系，服务于检查和测试选择。

契约变化时，识别生产方、消费者和相关组合链路，验证结构与语义影响。跨部署版本的兼容范围由实际发布约束确定，不默认为各端同时升级。

公用记忆模块维护自己的可执行公共契约、服务实现及按需生成的类型和薄客户端，当前宿主与工程组织以记忆架构（规范源相对路径：`capabilities/memory.md`）为源，各消费仓库锁定所用版本。消费者契约验证补充跨仓依赖关系；不直接导入其他仓库私有源码、共写记忆数据表或复制手写 Schema。领域内容契约的归属与公共接口分开，按记忆文档约定协作。

### 7.2 测试责任

| 验证范围 | 证明内容 |
|---|---|
| 单功能验证 | 真实功能在替代外部依赖下的输入输出、错误及副作用 |
| 场景组合验证 | 准备、选择、确认、调用顺序和结果处理 |
| 入口与接线验证 | 页面和聊天进入同一链路，真实依赖已经接入 |
| 模型任务评测 | 意图理解、参数提取、澄清、任务切换及类型化输出 |
| 集成与业务系统验证 | Portal 验证实际请求响应、权限、码表及接口承诺的业务结果；业务系统验证内部规则、事务与持久化 |
| 真机验证 | 设备权限、原生宿主、设备操作及产物生命周期 |

测试真实被测功能，替换网络、设备等外部边界。断言返回和状态，也断言不应发生的提交或其他副作用。异步请求、身份或资源会在等待期间变化时，按契约区分保持结果有效的更新与使旧操作失效的转换，让真实实现及消费者经历这些变化；标识再次出现不单独证明仍属于原操作。模拟模型输出不能证明理解准确，结构校验不能证明业务成功。

测试质量以真实行为断言为依据。迁移或合并测试时，按当前契约保留仍有效的行为保护、替换失效断言；共享单元的新增测试不代替尚未覆盖的消费者接线与副作用验证。覆盖报告纳入本次验收的源码，不以排除有效文件或削弱断言凑指标；预期来自契约，不复制实现算法。用例数据和资源隔离，等待异步工作及清理完成，并采用工程的测试超时约束。不稳定用例保留首次失败，重试通过不等于问题修复。

本地快速验证按影响范围执行。系统合并和发布按实际 CI 配置完成 required 验证，定向测试不能替代完整门禁；同一验证阶段避免重复执行相同测试。

### 7.2.1 日志与故障诊断

功能新增、修改或重构涉及外部依赖、持久化、异步收尾、异常转换、降级或恢复时，诊断属于同次实现与验收范围。沿实际调用链确认失败产生、转换、抑制及结果交付的位置，复用工程现有日志入口，在责任边界补齐必要记录。未改变这些路径的展示或文字调整沿用已有诊断。

记录应能区分操作、阶段、结果及可取得的底层原因。包装异常或转换失败结果时保留安全的错误类别、原始码、原因链和定位信息；关联固定于操作开始时，失效身份或已结束操作的迟到结果不能归入新的操作。正常取消、预期业务分支和技术故障分别分类；持续故障去重时保留原因变化与恢复记录，同一失败的详细原因由最有上下文的一层记录。

日志入口统一提供时间、级别、稳定的应用标识、模块和事件，再附操作关联、阶段、结果及安全诊断字段。可读格式采用 `UTC时间 LEVEL [应用] [模块] 事件 key=value`；应用标识如 `unif-portal`、`unif-agent`、`unif-marketing`，模块对应实际功能或源码归属。业务调用方不手工拼前缀；结构化记录保留独立字段，沿用所属工程命名，不为统一展示再复制一套日志。事件名稳定，不嵌入用户内容或动态 ID。

级别按实际影响和所属功能契约选择：`ERROR` 表示技术或契约异常、关键状态失败及无法继续的阶段；`WARN` 表示需关注的依赖失败、降级或可恢复异常；`INFO` 表示关键步骤、结果和状态恢复；`DEBUG` 表示开发排查细节。正常取消与合法业务分支不默认记为错误。调整展示格式不同时改变既有级别、采样、过滤和恢复策略；高频明细不进入生产 Info。

日志调用点与异常起点分开表达：可读字段 `log_source`／`log_function` 定位记录位置，`error_source`／`error_function` 定位可确认的故障来源。位置由运行时记录或已有异常栈自动提取，只保留安全的相对源码路径或文件名及有效行列，不手写行号，不把包装层位置当成根因。无法可靠取得时省略；压缩产物须结合对应版本的 sourcemap 才能定位源码。客户端 Info／Debug 不为定位另建调用栈。

日志字段按工程契约投影、脱敏并限制体积，不直接输出凭据、用户正文或任意请求／响应对象；无法取得的原因明确未知。可读输出转义换行及控制字符，避免伪造记录；不将任意异常文字解析成来源字段。记录失败不能改变业务返回、异常传播、权限、事务、资源归属、重试、恢复或用户提示，也不能递归写入已失败的日志通道。

测试除返回和状态外，还应验证受影响失败分支的诊断类别、阶段、关联与脱敏，覆盖取消、迟到、降级和日志自身失败等实际边界；格式或定位变化还需核对字段一致性、记录点与异常源的区分、重复记录及来源不可用的情况。断言业务副作用及原有保护保持有效。审查逐项核对新增或改变的失败路径是否仍可定位，不能仅凭通用错误码、界面提示或正常流程通过认定诊断完整。日志记录、自动化测试与真实环境可取得的信息分别说明。

### 7.3 变更影响

| 变化 | 验证范围 |
|---|---|
| 后端字段或响应包装变化，业务语义不变 | 原始协议校验、适配映射测试及必要联调；确认仍产出相同功能契约，不要求所有页面改动 |
| 功能内部变化 | 本功能及实际受影响的适配、消费者和组合 |
| 单个任务指令变化 | 该任务评测，必要的识别、切换和复合意图样本 |
| 共享契约或通用指令变化 | 受影响的生产方、消费者、任务和场景 |
| 共享状态变化 | 相关读写者、任务切换及异步结果交接 |
| 记忆公共接口、权限或生命周期变化 | 实际调用方的契约与相关组合；检索结果或装配语义受影响时补对应任务评测 |
| 设备适配变化 | 设备功能、相关场景和 H5 消费者；涉及原生行为时补真机验证 |

影响范围无法完整确定时，扩大到相关领域及集成链路，并补齐遗漏的依赖关系。完整验证发现的漏测问题用于修正定向选择规则。

### 7.4 设计交付的最小依据

设计说明按本次变化提供可检查的依据，不规定固定目录、文件模板或每函数一份文档：

- 能力、场景和入口各自承担什么，哪些处理仍为内部普通函数；职责调整后，原有已确认能力与业务行为由谁承接、通过什么接口衔接并验证；每个额外字段、状态、交互或调用对应哪个已确认需要和实际消费者。
- 场景每一步由谁触发、通过哪些已有参数、props、ref 或事件回调进入哪个功能；输入由谁准备，前一步输出如何交给下一步，结果如何回到展示。公共组件与所属业务场景之间的交接必须具体，不能只写“由 Portal／调用方处理”。已有接口足以承接时直接引用，不另建同义接口；已有数据的复用、刷新和后续调用归属明确，不能为定位既有业务目标而额外发起未授权的创建、提交或状态更新。
- 各结果状态能否由真实数据构造，接收者如何处理；文字描述、类型的必填／可选约束与验收样本必须一致。用于展示的空值不能补成业务身份或已满足的条件。
- 写明所属业务场景或应用功能，由它维护草稿、确认、请求与结果采用，公共展示组件只接收必要数据并交付事件；最终业务事实由所属业务系统处理与保存，取消和迟到结果仍有原归属。普通调用可由参数、返回值和局部状态完成时，不额外要求公共关联标识或运行机制。
- 外部依赖如何替换、谁实际消费该契约、优先验证哪些行为，以及什么变化需要扩大验证。

已有契约覆盖且公共语义不变的内部调整，引用对应依据和已有验证即可，不重复设计完整模块。设计定义验收范围，交付时提供实际执行证据；类型示例通过检查不能代替场景交接和业务语义审查。

纯能力按本次明确的输入输出及副作用完成设计，不需要预先穷举所有使用场景；本次范围包含交互或场景组合时，必须补齐该段事件、确认、调用和结果交接。尚待设计的其他流程在 STATUS.md 限定范围，不能以基础能力已完成代替完整场景已完成，也不由开发者补猜默认流程。
