# 架构与模块设计技能评测

这些是研发模型的设计与审查评测，不是产品运行时营销智能体评测。样本、评分标准和结果不进入技能默认上下文。

`cases/`、`rubric.md` 和本文件纳入版本管理。`runs/` 保存本地评测的固定输入、原始输出、日志及来源摘要，由 `.gitignore` 排除，不作为 CI 的默认输入。

## 来源边界

cases 中的需求、接口、依赖关系与实现建议是具体评测题设；“已确认”“已在使用”“实际关系”仅说明题目内成立的条件，不是对真实仓库的核验结论。简化或错误签名用于检验审查能力，模型输出是观察记录，都不能充当后续设计的正式 API、源码证据或必建接口清单。

真实设计先读取目标模块正式契约和本次需求，沿用已确认名称。没有契约时按职责提出草案；名称与旧样本相同或不同都不能单独决定对错。评分按职责、行为、副作用及真实或题设依赖关系，人工区分正式引用、候选、比较与反例，不做字符串黑名单。

活动 cases 与 rubric 可以随验证目标更新；runs 中的冻结输入、原始输出、manifest 和历史评分不回写。平台同步脚本只更新根规范快照，不负责递归同步领域 API 或改写评测方法名。

## 可重复执行方式

1. 固定同一份平台架构快照与 cases 样本。控制组只读取架构；技能组读取同一架构、SKILL.md 及其必要引用。
2. 每次使用全新上下文，给出相同用户任务。不要给被测模型 rubric、预期答案、其他运行产出或作者结论。
3. 声称技能相对仅架构的增益时，review 样本每组至少五次独立运行；版本维护按实际变化选择相关样本，同时修改规范和入口时分开记录旧包、仅更新规范、两者都更新的对照。记录使用的模型、来源文件哈希、允许读取的文件、完整输出；少量运行不能推断生产正确率或跨模型稳定性。
4. 依据 rubric 人工评分并摘录证据，保留不满足项。无基线失败时只能报告未观察到增益，不为得到漂亮数字修改评分标准。
5. 单独验证选择技能的边界；显式要求加载成功不等于自动发现有效。
6. 针对性来源边界验证使用 `provenance.md`；`rename-a.md` 与 `rename-b.md` 仅替换一个方法名，其余场景、职责、参数和副作用保持一致，分别在独立上下文运行后比较语义结论。新结果另建运行目录并记录所用活动样本与规范版本。

当前规范的针对性样本：`response.md` 检查成功码、展示缺项、嵌套读取及写入输入；`confirmation.md` 检查确认复用、需求范围与单能力验证；`switch.md` 检查单营销入口的自答／委派、类型化分析边界、引用隔离、意图切换和必要记忆。历史多领域题设仍按对应 runs 冻结的规范、输入及判据解释，不套用当前单营销条件。各样本按 rubric 的独立判据人工评阅，不向被测上下文提供该文件或判据。

运行成本只有在工具提供模型调用、Token、延迟时才报告对应数值。文件字节数是可重复的上下文体积指标，不等于 Token。新会话只验证独立上下文；压缩场景、其他模型、实际自动发现和业务工程实施需另测。

需要核对本地运行档案时，执行 `python scripts/validate_repository.py --include-evals`；缺少本地 runs 不影响分发包校验。
