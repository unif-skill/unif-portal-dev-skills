草案应把接口结果、读取展示和写入条件分开。营销接口按已确认的数值 `code: 200` 判定成功；成功后的数据缺项不改判接口失败。展示可以保留不完整数据，业务写入仍必须取得实际身份和必要输入。依据是所附平台规范第 6.1—6.3 节、第 6.4 节及第 7 节。

后端原始类型按接口应提供的完整数据定义，这一点成立。但它属于适配边界，不能直接作为整页展示的准入条件。运行时仍需检查码的类型、列表是否可读取及所用字段，读取视图则表达实际缺项；二者不因契约同源要求而合并成同一完整对象 Schema。

草案需要调整的处理是：

- 删除以完整对象校验拒绝整页、剔除缺值行和增加异常计数的设计。接口数组的条目数量及顺序全部保留，`null` 条目也保留其位置，展示字段为空。
- 将嵌套的读取字段设为可选。只有 `task`、`customer`、`address` 可选，仍会要求一旦对象存在就包含全部字段，不能表达题设数据。
- 区分实际空数组和缺少可读取列表。不得把缺少 `items` 统一补成 `[]`，从而宣称本页没有记录或业务没有匹配。
- 删除用列表索引补业务 ID 的处理。展示位置不具备业务身份；不能为了进入流程而伪造输入。
- 删除 `success_receipt_invalid` 及据此再次创建的处理。已知成功码下编号缺失，用可选编号表达，保留成功结果，停止依赖该编号的后续步骤。
- 公共传输层只处理传输、认证等技术事项。业务码由各领域对应端点的适配器解释，消费者接收语义结果，不再各自比较原始业务码。

以下名称仅用于说明本次边界，不定义额外后端 API。读取视图和写入输入的最小类型可以是：

```ts
interface TaskView {
  visitTaskId?: string;
  phase?: string;
}

interface CustomerView {
  customerId?: string;
  customerName?: string;
}

interface AddressView {
  city?: string;
  street?: string;
}

interface TaskRow {
  task?: TaskView;
  customer?: CustomerView;
  address?: AddressView;
}

interface TaskQuerySuccess {
  status: "success";
  // [] 表示本页无记录；缺省表示没有可读取的列表。
  // null 条目保留，不删除、不计为异常行。
  items?: Array<TaskRow | null>;
}

interface CompleteVisitInput {
  visitTaskId: string;
  customerId: string;
}

interface SaveReasonInput extends CompleteVisitInput {
  reasonId: string;
}

interface CreateSuccess {
  status: "success";
  id?: string;
}
```

读取时对可选对象、可选字段及 `null` 条目安全取值，缺失展示值按空显示。`TaskQuerySuccess` 和 `CreateSuccess` 仅表示成功分支，不能在缺码、未知码或传输失败时构造。写入输入的必填约束阻止直接把不完整读取对象当成提交对象；运行时还须从实际响应、有效的明确输入和用户选择中取得这些值，TypeScript 的 `string` 本身不能证明其是真实业务身份。原始协议和功能契约分别维护同源的类型与必要校验。

逐个响应的处理如下，各项独立判断，不相互补充数据：

| 响应 | 接口结果与展示 | 后续操作 |
|---|---|---|
| 1. 数值 `200`，三个数组条目 | 查询成功，依次保留三项。第一项状态、客户名为空，地址只展示“杭州”；第二项保留实际状态 `visiting`、客户名“店乙”和街道“二号路”，不补城市；第三项保留空行位置，展示字段为空。不剔除、不增加异常计数，也不推断缺失状态。 | 点击第一项后，实际 `V1`、`C1` 可供准备写入；若要保存原因，还必须有用户选择的 `reasonId`。第二项和第三项缺少实际身份，不能构造写入请求。保留其可展示数据，并在操作准备时说明必要信息不足。题设未提供补齐身份的能力，不能虚构查询或借助创建操作补齐。 |
| 2a. 数值 `200`，`items: []` | 查询成功，本页无记录。 | 不扩大成所有范围都没有业务匹配。 |
| 2b. 数值 `200`，`data: {}` | 查询成功，但没有可读取的列表，展示“暂无列表数据”。成功结果中 `items` 缺省。 | 不归一化成空数组，也不改判接口失败。 |
| 3. 保存原因数值 `200`，`data: false` | 保存原因接口成功；题设规定的继续条件不满足。不能因 `false` 把接口改判为失败或权限拒绝。 | 不调用完成拜访。场景按 `data === true` 的既定条件推进，不能用一般真值判断替代；可展示“保存原因接口已成功，但当前不满足继续完成拜访的条件”。 |
| 4. 创建数值 `200`，`data: {}` | 按创建成功处理，记录编号缺省。 | 读取详情需要真实编号，目前不能发起。展示“创建成功，暂未取得记录编号，无法读取详情”；不增加通用回执异常状态、不编造编号、不自动再次创建。题设未确认其他核实能力，不设计额外接口。 |
| 5a. 查询缺少 `code`，但有 `items: []` | 无法确认查询结果；数据存在或为空都不能证明成功。 | 不展示为成功查询的“本页无记录”。可展示“查询结果未确认”。 |
| 5b. 写请求超时 | 写入结果未确认，不能推断成功，也不能断言业务写入确定失败。 | 保留所属请求关联，展示“提交结果未确认”。是否核实或重试须有实际业务契约依据；题设没有提供这些能力，不能自动重发。 |
| 5c. 写响应字符串 `"200"`，带 `id: "N1"` | 营销端点未确认字符串码的含义，结果未确认。不能将字符串转成数值成功码，编号存在也不证明成功。 | 不推进依赖成功写入的步骤，不自动重发；原始码及编号可保留在该请求的诊断记录中。 |
| 6. 其他领域字符串 `"OK"`，`data: 0` | 该端点按已确认的字符串成功码判定成功，统计值为有效的 `0`。 | 正常展示 `0`，不能用 `if (!data)` 判为失败或缺失，也不能被营销码规则拦截。 |

营销端点若返回数值 `403`，适配器映射为已确认的权限拒绝，场景停止依赖该操作成功的步骤。其他未确认码值保持结果未确认，不补造码表、失败分类或重试规则。原始码和请求关联留在适配结果解释及诊断中；页面、场景使用映射后的结果。

职责上，查询功能只读取并交付可展示的快照；适配器负责业务码解释和字段读取；场景负责点击后的输入准备、用户选择与确认，以及保存原因后是否继续完成拜访。点击题设中的列表项只表示开始准备，不能自动扩张为写入确认。业务系统负责最终权限、规则和业务事实。保存原因的成功、继续条件不满足及完成拜访尚未执行，应分别保留其真实含义，不能合并为整个场景失败或完成。

必要验收应覆盖以下边界：

1. 对真实查询适配器替换网络依赖，输入第 1 项响应，断言输出三项且顺序不变、第三项仍为 `null`，并在读取展示验证缺失字段为空。没有整页拒绝、过滤和新增异常计数。
2. 分别输入 `items: []` 与缺失 `items` 的成功响应，断言二者均成功但读取状态不同，并验证用户分别看到“本页无记录”和“暂无列表数据”。
3. 类型检查验证第一、第二条不完整记录及 `null` 可以进入读取视图；缺少任何必需 ID 的对象不能用作对应写入输入。场景验证实际身份缺失时写请求次数为零，索引和展示空值从不进入业务请求；保存原因必须使用用户实际选择的 `reasonId`。
4. 对保存原因的 `200/false` 断言接口成功、继续条件不满足、完成拜访调用次数为零；补一个符合既定条件的 `200/true` 对照，验证具备必要输入与确认时允许继续，而不是把所有布尔数据一律阻断。
5. 对创建的 `200/{}` 断言成功且编号缺省；详情调用次数为零，创建请求总次数仍为一次，不出现 `success_receipt_invalid`，并验证对应中文提示。
6. 对缺码、写超时、字符串 `"200"` 及一个未确认码，断言结果未确认，不能因空数组、非空编号或 HTTP 层成功而推进；数值 `403` 断言权限拒绝。验证相关结果仍归属原请求，并且没有自动重发。
7. 对其他领域的 `"OK"/0` 验证成功并展示 `0`。若公共传输代码确有改动，验证营销与该领域的实际适配消费者都保持各自码语义；不要只验证营销数值 `200`。

这些是设计验收要求，尚未实施或运行测试。题设已确认的码与业务条件足以支持以上结论；真实系统接线、业务事务及其他码的含义均未在本任务中核实。
