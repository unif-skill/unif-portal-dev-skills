# A、B、C 设计审查结论

依据本次提供的《Unif 平台架构》及 architecture-design 技能。A 需补齐关键交接契约；B 保留字段适配、删除无依据增强；C 按既有授权进行等价内部调整。本次仅完成设计审查，以下验证均为实施验收要求，未运行代码、测试或联调。

## A. 完成拜访：调整后推进，不能以类型编译通过判定链路成立

保留已确认链路：营销智能体输出客户查询条件 → Portal 调用共用客户查询并完成客户选择 → 取得既有拜访任务引用 → 与手动入口进入同一完成场景 → 准备、确认、提交 → 按业务系统结果展示。Agent 不构造任务身份、不执行查询或提交，也不承担确定性流程。

现有契约存在实际断点：`getVisitTask` 的输入已经要求 `VisitTaskRef`，不能把 `CustomerRef` 转成任务引用；`acquireVisitTask` 可能创建任务，不能用于完成场景寻找既有任务。保留它在开始场景中的已确认用途，明确其写入副作用与相应确认责任。可复用其内部纯查询实现，但不能调用整个 acquire 流程，也不通过新增一个含混开关掩盖两种职责。

**必要公共接口与结果：**

- 补齐“按客户只读查询既有任务”的交接。若已有等价只读接口则直接复用，否则提供一个小型查询接口；真实消费者为完成场景，以及开始场景中相同语义的查询部分。候选必须包含完整、有效且与所选客户一致的 `VisitTaskRef`。接口草案如下，查询范围及完整性判据受待确认项 A1 约束，尚不能按此自行推导日期、计划或分页规则。

  ```ts
  declare function findExistingVisitTasks(input: {
    customer: CustomerRef;
  }): Promise<
    | {
        status: 'success';
        tasks: readonly VisitTaskSnapshot[];
        coverage: 'complete' | 'partial' | 'unknown';
      }
    | { status: 'failed'; reason: 'business_rejected' | 'transport' | 'invalid_response' }
  >;
  ```

  `complete` 仅指业务已定义的查询范围已被覆盖。只有该范围完整且候选为空，才能表达“该范围内没有任务”；失败、部分页或范围不明不能转成无任务。候选存在也不意味着唯一，不自行选最新、首条或任意计划任务；多候选由场景完成明确选择。找不到有效身份时停止完成提交，不创建、补默认身份或让模型猜测。取得引用后可按实际需要调用 `getVisitTask` 核对快照，不为复用而重复查询。

- 将“查询完成条件、处理资产差异”落到具体能力。建议先定义一个只读的完成准备查询：输入 `VisitTaskRef`，输出可继续所需材料、明确阻断或准备结果无法取得等分支。哪些条件及资产字段必要仍属 A2，不能在草案中写成已具备能力。字段整理和差异计算优先留在内部普通函数；若差异处理产生业务写入，必须明确独立操作或已确认的完成请求内容、确认责任及部分成功结果，不能隐藏在准备查询中。
- `completeVisit({ ref })` 可保留最小输入，只有 A2 确认需要其他提交内容时才扩展。用类型化结果替代 `Promise<unknown>`，至少区分 `success`、`rejected`、`unconfirmed`、`success_receipt_invalid`；成功回执所需字段由 A3 确认，不能以输入引用伪装后端回执。适配器校验原始协议、按明确业务码映射，保留原始码与请求关联供诊断；消费者不再比较具体后端码。写入超时、缺码、未知码不能推断成功或确定失败；成功码可信而必要回执损坏时保留成功证据，不能按普通失败重提。

**开始条件类型也须修正。** 当前 `VisitStartRequirements` 强制所有分支带位置和距离，无法表达业务已允许的“只返回禁访”或“位置配置暂不可用”。采用判别联合：`blocked` 和 `unknown` 不要求位置；`allowed` 下再区分配置 `available` 与 `unavailable`，仅 `available` 要求真实目的地和距离配置。禁访不因缺位置而成为解析错误；允许但配置缺失不等于准备完成。不得填零坐标、默认距离或伪造放行。具体缺失原因及继续条件按外部约定确认，不让完成场景无依据依赖开始条件。

**状态与确认：** 完成场景持有已选任务、准备材料、待确认内容及提交状态；手动与聊天复用同一份状态和调用过程。确认绑定本次具体任务及最终提交内容，内容变化后旧确认失效，无需重复弹窗。提交前取消停止后续写入；发出后取消等待不等于撤销，迟到响应仍归属原请求和交互。最终完成以业务系统码表和有效回执为准，查询快照不替代提交时的规则校验。

**实际验证范围：**

- 真实既有任务查询与适配：完整空结果、多候选、部分分页、未知覆盖范围、查询失败、身份缺失及客户不匹配；断言整个完成查找过程不调用创建操作。
- 共用完成场景与两入口接线：从仅有客户条件走到合法引用、准备、确认及提交；覆盖无引用不提交、确认内容变化、取消、迟到结果及资产步骤的真实副作用。若资产步骤存在独立写入，验证部分成功不被整体失败覆盖。
- 完成请求适配：明确成功与拒绝、未知或缺失业务码、超时、成功但回执异常；不得依据 HTTP、非空数据或业务 ID 宣告成功。核对各结果实际展示的简体中文。
- 开始条件契约的生产方、开始场景及其他真实消费者：禁访且无配置、结论未知、允许但配置缺失、允许且配置完整。只有涉及设备实现或原生行为变化时补对应真机验证。
- 完成任务的模型评测覆盖客户条件提取、必要澄清和不编造任务引用；若改动任务指令，补相关识别、切换和复合意图样本。模拟模型输出只证明接线，不能证明理解准确。A1—A3 的规则、码表及最终事实须通过真实接口核实；定向验证不替代现有 required 检查。

**待确认业务事实：** A1：任务查询的日期、计划、分页覆盖、可选任务范围和唯一性依据；A2：完成条件、资产差异的业务含义、是否写入及所需确认；A3：完成接口各业务码的类型和含义、必要回执，以及是否支持结果核实、幂等或撤销。以上是本次审查的独立缺口记录；定稿时同步正文契约与验收，不另存第二套有效规范。无需等待这些事实才能否定 acquire 的错误复用，或完成其余已确认边界设计。

## B. 照片适配：只保留 objectUrl 到 uri 的映射

维持 `visitPhotoAdapter` 的职责与公共成功结果 `{ uri }`。原始成功响应按数值 `code === 200` 校验，并将有效 `data.objectUrl` 映射成 `uri`；不新增公共接口，不要求同时兼容旧字段。公共传输层 `uploadBinary` 不解析这项业务码表。

删除“两次失败重试”和“缺 code 但存在 objectUrl 即成功”的建议：两者均超出已确认需求，前者改变请求次数和副作用，后者伪造业务成功。异常沿所属功能的现有语义处理；可信成功码下必要 objectUrl 损坏，应保留成功证据并表达回执异常，不自动重传。缺码或未知码不能返回成功 uri；HTTP 200、字符串 `"200"`、非空 objectUrl 均不能替代数值业务成功码。原始技术错误不直接显示给用户。

优先更新已有真实适配测试；缺少必要分支时再补断言，不另建只复制映射逻辑的测试。替换外部上传边界，验证数值 200 与有效 objectUrl 的映射、明确失败码、字符串码、缺码、未知码及成功码下无效回执，同时断言每次操作只发出原本一次请求。检查店头照和自拍照两个实际消费者接收相同 uri、沿用已有异常展示与流程；优先执行其现有相关测试，不重复证明相同内部映射。

本次未改 `uploadBinary`，H5 与问卷不调用 `visitPhotoAdapter`，因此不因同用上传能力就扩大到它们，也无需新增真机验证。“以后所有修改只跑这个测试”不成立：以后若改变公共结果、取消、资源释放或共享执行逻辑，应重新检查相关读写者与调用链；触及 `uploadBinary` 时包括 H5、问卷等实际消费者，触及原生行为时补真机验证。发布 required 检查保持现有配置。实际后端新响应还需必要联调，确认业务码及映射符合外部契约。

## C. 私有名称整理：沿用授权和现有验证

保留为客户查询适配模块内的普通私有函数，供两段等价逻辑调用；不增加公共导出、独立模块、通用转换机制、设计文档或审批步骤。实现者按已有授权直接提取，维持输入输出、排序、请求次数、副作用及公共契约。

运行已有覆盖两段分支的真实适配测试，并检查变更与相关静态检查结果。既有断言充分时不新增镜像测试，不扩大到无关页面、模型评测或真机验证；交付阶段继续遵循现有 required 检查。本次审查不执行产品代码修改，亦不宣称该调整或测试已完成。
