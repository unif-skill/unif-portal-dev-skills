**A. 完成拜访：保留共同场景，补齐只读任务交接后才能实施完整链路。**

保留已确认行为：营销智能体只输出客户查询条件，Portal 查询、选择客户，再进入手动入口共用的完成场景。Agent 不查业务系统、不生成任务身份、不确认或提交。类型示例编译通过只证明类型可接受，尚不能证明调用链路完整。

目前客户选择只能得到 `CustomerRef`，而 `getVisitTask` 和 `completeVisit` 都要求 `VisitTaskRef`。`acquireVisitTask` 可能创建任务，不能用于完成场景的查找或无结果兜底。它在开始场景的既有用途可以保留，但必须明确其创建副作用及对应确认责任，不能描述为纯查询。

需要补充或复用语义等价的只读公共能力，以下为草案，受文末待确认项 A1 约束：

```ts
type ExistingVisitTasksResult =
  | {
      kind: 'candidates';
      tasks: VisitTaskSnapshot[];
      coverage: 'complete' | 'partial' | 'unknown';
    }
  | { kind: 'unavailable' }
  | { kind: 'queryFailed' };

declare function findExistingVisitTasks(input: {
  customer: CustomerRef;
}): Promise<ExistingVisitTasksResult>;
```

`complete` 仅表示已确认查询范围内覆盖完整。空候选只有在该条件成立时才能说明范围内没有任务；部分页、查询失败和范围未知不能转换成“无任务”。返回引用必须来自业务系统，并与已选客户一致。多个候选不能擅自选择最新一条；任务选择或唯一性规则按 A1 确认，不据此预定新增页面或弹窗。外部系统若不支持按客户取得既有任务，应报告能力缺口，不能用创建能力或伪造 ID 补齐。`getVisitTask` 继续用于已知引用的查询，`null` 只表示契约明确的未找到。

完成链路为：客户查询与选择 → 只读取得既有任务候选 → 按明确规则取得真实引用 → 已确认必要的完成准备 → Portal 确认具体内容 → `completeVisit` → 展示业务回执。无任务、歧义未解决、查询失败或取消均不提交。任务快照用于展示和准备，不能取代提交时的最终规则校验。

草案中的“查询完成条件、处理资产差异”尚无可实现契约：其业务必要性及具体内容按 A2 确认。需要外部读取时定义对应只读输入、结果及失败；纯整理保留为私有函数；若涉及资产写入，须另列操作契约、确认责任和部分成功处理，不能藏在准备阶段。不把开始条件当作完成条件，也不由 Portal 复制业务准入规则。

必要契约调整还有两处：

- `completeVisit` 不再返回 `unknown`。公共结果至少区分业务成功、明确业务拒绝、结果未确认，以及成功码可信但必要回执异常；实际其他状态按 A2 的接口契约表达。适配器校验原始响应并解释业务码，保留原始码和请求关联；消费者不比较后端码。超时、缺码、未知码不推断成功或确定失败；成功但回执异常不能按普通失败再次提交。
- `VisitStartRequirements` 不能要求所有分支都有位置配置。改为可区分的结果：`admission: 'blocked'` 可仅含禁访结论，`admission: 'unknown'` 表达未能确定；`admission: 'allowed'` 再区分位置配置可用或不可用。只有配置可用分支携带真实目的地及两个距离阈值。配置不可用不等于禁访，也不能补零或默认坐标。网络失败另行表达，不冒充业务结论。

草稿、选择及确认由所属 Portal 场景维护。确认关联真实任务引用和实际提交内容，内容变化后重新确认，不必增加弹窗。请求及迟到响应归属原操作；发出写请求后取消等待不表示业务撤销。核实、重试、幂等或补偿仅采用业务系统已支持的能力。

验证范围：使用真实查询、适配及场景代码，替换网络边界，覆盖客户到任务引用交接、空结果与查询失败的区别、分页覆盖不足、多候选、客户引用不匹配，以及所有停止分支不创建任务、不提交。验证手动与聊天进入同一完成场景、确认内容变化及迟到响应归属；完成适配覆盖码表、回执异常与结果未确认。开始场景补验禁访无配置、准入未知、允许但配置缺失及配置完整分支。模型任务评测验证完成意图、客户条件、必要澄清与任务切换，不能以模拟模型输出代替理解评测。外部接口联调验证任务身份、查询范围和最终完成事实；仅当实际设备链路受影响时补真机验证。

**B. 照片适配：仅保留已确认的响应字段映射。**

在 `visitPhotoAdapter` 的原始响应契约及映射中，将 `data.url` 改为 `data.objectUrl`，成功公共结果仍为 `{ uri }`；无需新增公共接口、兼容回退或转换框架。删除顺带增加的两次重试，当前没有相应需求或幂等依据。缺少 `code` 时即使有 `objectUrl` 也不能返回成功；只认数值 `200`，不强转字符串码，也不以 HTTP 状态替代业务码。已知成功码但必要 `objectUrl` 损坏，应保留成功证据并表达回执异常。
