# 多入口与任务切换设计

依据附带《Unif 平台架构》第 2—7 节；来源为 `unif-platform-architecture/ARCHITECTURE.md`，快照 SHA-256 为 `8d8ff684c9216b3d630b87e260201282032c7f8ddd5d348a6234249d2a24a321`。本次交付为契约与调用设计，不实现产品代码。下述接口名用于表达必要边界，不代表对应业务接口已经存在；尚缺领域依据的部分标为草案并关联文末待确认项。

## 推荐边界

营销领域保留一个智能体，拜访和下单分别维护任务指令、类型化契约和评测样本。Portal 负责场景组合、客户引用、草稿、确认、业务调用和结果展示；模型只输出理解结果。客户查询由普通入口和自然语言入口复用同一查询功能。

| 边界 | 本次职责与实际消费者 |
|---|---|
| 普通客户查询入口 | 将查询框输入转换为查询条件，直接调用客户查询并展示列表。 |
| 自然语言入口 | 提交发话文本与本次必要引用，接收并校验类型化理解结果；查询交给同一查询功能，业务目标交给对应场景。 |
| 下单场景 | 持有订单客户与本地草稿，解析商品候选、收集必要输入、维护确认并调用订单提交功能。手动下单与 AI 下单共同使用。 |
| 完成拜访场景 | 取得明确拜访引用，组织资产差异处理、确认和完成操作。手动按钮与 AI 完成拜访共同使用。 |
| 查询、订单提交、完成拜访等独立功能 | 按明确输入访问业务系统；由适配器解释原始协议和业务码，向场景返回语义结果。 |
| 营销智能体 | 按需装配通用指令和当前任务内容，识别意图、提取参数、处理必要澄清；不访问业务系统，不执行确认或提交。 |

字段整理、查询结果投影、资产差异的确定性计算、草稿更新及确认版本校验保留为所属功能或场景的普通函数。复用对象是查询功能与场景调用链，不为本次需求增加通用路由框架、统一任务状态容器或每任务一个智能体。

实现建议中的四项需要调整：

- “所有请求先经过一次模型路由”改为按需识别。普通查询不调用模型；领域或任务已经明确时由代码选取对应处理内容。
- “营销每轮加载全部任务指令和查询列表”改为只装配本次理解需要的内容。本例下单加载下单任务；自然语言客户查询只提取条件，不加载查询结果列表。
- “AI 直接调用 completeVisit”改为 AI 和手动按钮进入同一个完成拜访场景，资产差异处理与确认只有一份责任和实现。
- “全局 selectedCustomer 统一拜访和订单客户”改为各交互持有自己的明确引用，通过类型化输入显式交接。列表选择只维护列表交互的选择。

## 本次请求与任务交接契约

实体引用表示已确定的身份，不以客户名称代替。以下为边界形状示意；实际类型、运行时校验和模型 Schema 应从同一份可执行契约取得，不在提示词中手写第二份字段定义。

```text
CustomerRef = { customerId }
VisitRef = { visitId }

InterpretRequest = {
  requestId,
  text,
  taskHint?,
  refs: { customerRef?, visitRef? },
  necessaryContext?
}

Interpretation =
  | { kind: "order.prepare", customerRef,
      lines: [{ productText, quantity, requestedUnit }] }
  | { kind: "visit.complete", target:
      { kind: "visit", visitRef }
      | { kind: "customer", customerRef } }
  | { kind: "customer.query", conditions: CustomerQuery }
  | { kind: "clarify", subject, missingInformation }
```

`requestId` 是 Portal 创建的关联标识，传输层将响应关联回原请求，不能以模型任意生成或修改的标识选择写入目标。Portal 在发话时另行保存不可被列表选择修改的请求记录：所属交互、引用快照、当前处理阶段及是否已取消。所属交互等纯客户端协调信息不必全部进入模型上下文。

`taskHint` 只是线索。当前处于拜访，不限制新请求只能使用拜访任务。示例中的“给这家店下两箱商品甲”表达下单；任务选择应转到下单，`这家店` 使用发话时明确的 A 引用。模型返回的客户引用必须与本次允许使用的明确引用一致；本例返回 B、未知身份或缺失客户时不能进入订单提交，也不能重新读取当前列表选择来补齐。

任务明确时，普通代码根据入口信息、类型化事件或经过验证的确定性选择规则装配对应任务，不固定增加一次独立模型路由。若自由文本无法被可靠判定，则使用必要的最小意图识别或澄清，再选择任务；不能为追求一次调用强行分类。营销领域已经明确时不重复用模型做领域路由；跨领域且领域不明的自然语言请求才需要超级智能体识别领域。

一次装配包括营销通用指令、选中的任务指令、所需契约、发话文本和必要引用。本例没有订单草稿，不能提供或假造旧订单草稿；A 引用足以支持“这家店”的解析，不需要整个客户列表。客户查询使用最小的条件提取内容。复合请求只加载涉及的任务内容；模型可以提取用户表达的先后关系，实际执行必须服从已定义的 Portal 场景组合，未定义关系见 Q4。

## 客户 A 的下单调用过程

必要公共边界如下。商品查询和订单原始接口尚未提供，涉及字段的部分为草案，见 Q1、Q3。

| 契约 | 输入 → 输出 | 副作用与边界 |
|---|---|---|
| `prepareOrder` 场景入口 | 明确 `customerRef`、意向商品行、原请求关联 → 所属订单交互及本地草稿状态 | 创建或更新客户端订单草稿；不暗中创建服务端订单。 |
| `queryOrderProducts` | 商品检索条件 → 明确商品引用、展示信息及下单需要的单位信息，或明确查询失败 | 只读。候选不能被当成用户已经选择的商品。实际检索字段、单位规则待确认。 |
| `submitOrder` | 明确客户引用、商品引用、数量、单位及业务接口要求的其他完整输入 → 订单写入结果 | 业务写入，只能由场景在相应确认有效后调用。不能假设客户加两箱商品就覆盖了全部接口必填项。 |

具体时序：

1. 发话发生时，Portal 从本次拜访交互取得明确客户 A，将其值存入请求 R 的引用快照。R 此时没有订单草稿；不为理解用户的话预先创建业务订单。
2. 用 R 的文本和 A 引用理解下单任务，期望获得 `order.prepare`：客户 A、商品文本“商品甲”、数量 `2`、单位文本“箱”。输出的结构合法性、引用与数量单位语义分别校验。
3. 用户在查询列表选中 B，只更新列表交互的选择。它不修改 R 的 A 引用，不修改拜访 A 的业务归属，也不等于取消 R。
4. R 的响应到达后，Portal 根据请求关联找到 R，校验其仍可接收理解结果，并把捕获的 A 引用显式交给 `prepareOrder`。此时为 R 建立属于 A 的订单交互和本地草稿。任何后续步骤都不得在异步返回后重新读取全局 `selectedCustomer` 决定订单客户。
5. 草稿中的“商品甲”仍是意向文本。场景通过 `queryOrderProducts` 获得可用于订单请求的商品与单位身份；依照已确认的消歧规则取得明确商品，存在歧义时由用户选择或澄清。无候选应明确展示；查询失败不能伪装为无候选。不得自动取第一条，也不得猜测“箱”的换算关系。
6. 明确的商品引用、数量 `2`、经核实的箱单位与客户 A 组成可提交草稿。其他必要字段由已确认的业务接口决定；缺少输入时收集输入，不补默认业务规则。
7. 下单场景维护对具体草稿内容的确认，入口展示客户 A、商品、数量单位及其余实际提交内容。确认关联此订单交互的草稿版本；相关内容改变，原确认失效。使用对应交互的确认动作，不要求额外弹窗；模型输出不是用户确认。
8. 确认有效且输入完整后，场景把该草稿转换为 `submitOrder` 的请求。适配器根据本次响应的业务 `code` 解释结果，结果只更新这笔 A 订单的所属交互。

订单草稿一旦建立，其客户归属属于下单交互。拜访客户、订单客户和列表选中客户可以同时分别存在，不共同引用一个可变的客户选择对象。跨任务承接的是发话时的 A 身份，不是对全局选择的动态读取。

取消与迟到处理遵循原操作归属：理解或准备阶段明确取消 R，后到的模型结果不得重新创建草稿或推进提交；单纯选中 B 不触发这一取消。写请求已经发出后取消等待，不能显示业务已撤销；迟到回执仍记录至原 A 订单。请求关联与一次结果消费由所属交互维护，不另建统一的全领域状态机。

## 完成拜访的共同场景

AI 输出 `visit.complete` 后，由 Portal 校验目标并调用 `completeVisitScene`；手动按钮将其明确目标转换为同样输入后调用该场景。两者都不能绕过资产差异处理和确认。

| 步骤 | 对应契约或场景内处理 | 交接依据 |
|---|---|---|
| 确定既有拜访 | 已有明确 `VisitRef` 时直接使用；只有 `CustomerRef` 时调用只读 `findExistingVisitsForCompletion`，草案见 Q2 | 返回真实候选拜访引用。无候选则不能完成拜访，多候选由用户明确选择；不能用可能创建拜访的“开始拜访”或“准备拜访”操作替代查找。 |
| 收集完成所需数据 | 只读 `queryVisitCompletionData({ visitRef })`，草案见 Q2 | 取得资产核对及完成操作实际要求的数据；不能以客户 ID 冒充拜访 ID。 |
| 处理资产差异 | 场景共用的普通代码与交互，规则见 Q2 | 计算和展示差异，收集已确认规则要求的处理选择。不能由模型决定忽略差异或自动修正资产。 |
| 确认 | 场景持有完成草稿与确认依据 | 确认绑定明确拜访、资产处理内容及其他实际提交项；任一相关内容变更后重新取得有效确认。入口只负责展示和传递动作。 |
| 提交与展示 | `completeVisit(VisitCompletionRequest)` → 拜访写入结果，原始字段与码表见 Q2、Q3 | 只有完成场景在必要输入与确认齐备后调用；按业务码映射后的状态处理真实结果。 |

`findExistingVisitsForCompletion` 和 `queryVisitCompletionData` 是本设计要求核实的只读能力，并非声称当前业务系统已有这些接口。只读查找没有真实支持时，只有客户引用的分支存在交接缺口，应停在缺少拜访引用；已有明确拜访引用的部分仍可设计和验证。

资产差异处理是否包含独立业务写入尚不明确。读取与本地计算可以放在准备阶段；如果处理动作会写入资产业务数据，就必须明确相应写入契约、确认覆盖内容和每一步结果后再实施。不能隐藏在“准备”中，也不能假定 `completeVisit` 自动包含该事务。多次写入的先后和部分成功处理依据业务系统契约确定，不自行增加补偿、自动重试或跨请求事务。

该设计不新设一套拜访规则。手动入口已经承担的差异处理和确认责任应归入共同场景；具体规则缺口保留在 Q2，AI 与手动共同受它约束。

## 普通与自然语言客户查询

唯一查询功能：

```text
queryCustomers(CustomerQuery)
  → 查询成功及客户列表
  | 明确业务拒绝
  | 查询失败及可处理的原因
```

`CustomerQuery` 的实际支持字段尚未提供，见 Q1；普通查询框构造条件与模型条件提取必须使用同一语义契约。功能按条件读取数据，不替用户选择客户，也不触发拜访、创建草稿或业务写入。

- 普通入口：查询框输入 → Portal 输入转换与校验 → `queryCustomers` → 直接展示列表。模型调用数为零。
- 自然语言入口：用户文本 → 条件提取 → Portal 运行时校验 `CustomerQuery` → 同一 `queryCustomers` → 直接展示列表。明确条件的一般路径只需要条件提取这一轮模型调用，不把查询列表再送回模型总结。
- 条件无法确定时，提取结果提出必要澄清，不编造筛选条件。查询成功但列表为空是真实空结果；传输或协议异常不是空结果。

本次客户查询没有续推理需求，因此不提供整页客户列表给模型。若后续另有已确认需求需要模型在查询数据上继续推理，应由模型表达类型化数据需求，Portal 调用同一查询功能，再按该任务需要投影字段和限制数量；投影是普通函数，不能产生另一套查询核心，也不能把有限候选解释为全量数据。

## 业务结果与确认的最小语义

订单提交和完成拜访的适配器分别依据已确认的原始业务码表进行映射；传输层负责认证与通信。页面、场景和 Agent 使用功能语义，不重复比较原始业务码。两项功能至少要能让消费者区分以下证据：

| 结果 | 构造依据 | 场景处理 |
|---|---|---|
| `success` | 已知成功业务码，且必要回执有效 | 展示对应原操作的业务成功与有效回执。 |
| `rejected` | 已知业务拒绝码 | 展示明确拒绝，依据用户动作处理后续；不能改成成功。 |
| `successReceiptInvalid` | 成功业务码可信，但必要回执缺失或损坏 | 保留成功证据，说明回执异常；不能按普通失败再次提交。 |
| `unconfirmed` | 写请求超时、缺码、未知码等使业务结果无法确认 | 保留请求关联；仅在业务系统实际支持时查询核实，否则展示结果未确认。 |

原始码与请求关联保留在适配结果解释及诊断记录中。HTTP 成功、返回业务 ID、非空数据或模型声称成功都不是业务成功依据。其他已知业务状态按具体接口契约补足，不能猜测码值或自动将字符串码转成数字码。是否重试、幂等、撤销和核实均见 Q3，不因抽出共同场景增加这些行为。

确认由对应 Portal 场景维护一次，绑定实际提交内容。理解结果、列表选择、设备权限都不能替代提交确认。界面使用中文结果与提示，但提示文案不改变上述结果类别。

## 必要评测与验收

以下均为实施后的验证计划，本次没有执行模型评测、功能测试、真实接口或真机验证。

| 验证层 | 必要样本和断言 |
|---|---|
| 任务评测 | 拜访、下单分别维护意图、参数、引用、必要澄清和输出语义样本。客户查询验证自然语言条件提取，不只检查 JSON 能否解析。 |
| 识别与切换评测 | 当前任务为拜访时输入“给这家店下两箱商品甲”，应选择下单，客户为本次 A，商品文本、数量和单位正确；反向切换、任务不明确、缺少可解析客户引用、必要澄清也需覆盖。任务线索不能锁死新任务。 |
| 复合意图评测 | 例如明确表达先完成拜访再下单时，提取实际涉及的任务和先后；关系不明时不得自行排序。只装配所需任务，未定义的执行组合不因模型输出而自动执行。 |
| A/B 异步场景 | 运行真实下单场景和请求关联代码，延迟模型响应：发话时 A、无订单草稿，随后列表选择 B，再返回理解。断言草稿与后续提交仍属于 A、B 状态未被该响应改写；取消 R 后迟到结果不得复活；写入后迟到回执仍归原订单。模拟模型输出只证明接收链路，不证明模型理解准确。 |
| 完成拜访场景与入口 | AI 和手动按钮运行同一真实场景，覆盖有拜访引用、只有客户引用、零候选、多候选、资产差异处理、确认内容变更和取消。断言未满足准备或确认时不调用完成操作，AI 不存在直连提交捷径。 |
| 查询功能与入口 | 单独导入真实客户查询功能，替换网络边界，验证条件、空列表、业务拒绝和异常。接线测试证明两个入口使用同一查询功能、普通查询零模型调用、查询不发生业务写入、自然语言查询结果不触发无必要的模型续轮。 |
| 商品与写入适配 | 运行真实查询、订单及拜访功能，替换外部通信，覆盖商品身份及单位交接、业务码、合法空值、未知码、缺码、成功回执异常和超时。断言未确认结果与回执异常不自动重提。 |
| 真实接口验证 | 在接口契约确认后核对码表、字段、权限、必要身份、资产处理副作用和最终业务事实。替代依赖测试不能证明这些外部事实。若实际拜访链路涉及原生设备能力，再补相关真机验证，本次不额外增加设备步骤。 |

类型、运行时校验和模型 Schema 同源生成后，分别检查结构合法、引用与任务语义准确、业务系统最终判定；三种验证不能互相替代。模型成本记录完整目标中的路由、识别、澄清和续推理调用数，以及总 Token 与延迟，不承诺模糊请求都能一轮完成。

变更影响按实际消费者选择：单改下单指令验证下单及相关识别、切换、复合样本；改通用指令或上下文装配扩大到拜访、下单和客户查询提取；改请求引用或共享状态覆盖所有相关读写者及迟到交接。改 `CustomerQuery` 时同时检查查询框、自然语言提取的 Schema 与指令引用、真实查询适配及实际场景消费者。不能只靠静态 import 找消费者，还要核对模型 Schema、跨边界消息及实际存在的非静态协议消费关系。范围不能可靠确定时扩大到相关营销链路。发布 required 检查以实际工程 CI 为准，定向验证不替代发布门禁。

## 待确认项与影响
