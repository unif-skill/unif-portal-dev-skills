# 模块设计审查结论

本次仅形成设计与验收要求，未实现产品代码、未执行测试。A 需要补齐任务定位和副作用边界；B 收敛为响应字段适配；C 按已有授权完成私有函数抽取即可。

## A. 完成拜访

**调整后通过设计方向，任务查询范围与完成接口语义确认前，不能认定链路已经可实现或可验收。**

保留“营销智能体提取客户查询条件 → Portal 查询并选择客户 → 进入手动、聊天共用的完成场景”。智能体不生成任务身份、不选择业务事实、不提交业务请求。客户选择和拜访任务定位是两个步骤；选中客户本身不能提供 `VisitTaskRef`。

`getVisitTask({ ref })` 只能按已有身份读取快照，不能解决客户到任务的定位。`acquireVisitTask` 可能创建任务，不能作为完成场景的准备步骤使用。保留它在开始场景中的复用，但必须明确创建副作用及其确认责任。可以复用其中真实的只读查询实现，不能连同“没有就创建”一起复用。

必要公共接口保持在功能边界：

| 接口 | 设计结论 |
|---|---|
| 已有客户查询 | 输出真实客户候选，供 Portal 选择；无需新增一套聊天查询核心。 |
| `findVisitTasksForCompletion({ customer })` | 新增或公开已有的只读任务查找能力。返回真实任务候选、查询覆盖情况及明确的查询异常；不创建、不完成、不替用户选择。具体查询范围为草案，关联待确认项 A1。 |
| `getVisitTask({ ref })` | 保留精确查询用途。真实未找到与传输失败、业务拒绝、响应异常分别表达；不得都折叠成 `null`。 |
| 完成条件查询 | 只接收真实任务引用，返回完成场景需要的条件与差异信息。优先复用已有功能；具体字段和含义待 A2 确认，不照搬开始条件。 |
| `completeVisit({ ref, ...已确认的必要提交内容 })` | 将 `Promise<unknown>` 收敛为类型化结果，区分成功、明确业务拒绝、结果未确认、业务成功但回执异常。提交字段依 A2 定稿，不预设额外字段。 |

任务查找结果至少能区分“候选及完整覆盖”“候选及覆盖不完整或未知”“查询失败”。只有明确查询范围且完整覆盖时，空候选才代表该范围没有任务。分页未覆盖或范围不明不能判定不存在；取得更多结果只能使用实际支持的查询能力。多个候选由 Portal 呈现必要信息并完成选择，不能自行规定取最新、当天或第一个。没有可定位的真实任务时停止后续完成提交，不创建任务、不拼造 ID。任务引用必须与所选客户一致；快照中的 `phase` 不替代业务系统的最终完成判定。

共用完成场景明确推进：定位任务 → 查询完成条件 → 展示与处理必要差异 → 对具体提交内容确认 → 发出完成请求 → 展示真实结果。草稿、所选引用、确认依据和提交状态归该场景；内容变化使对应确认失效，异步响应按原请求与交互归属接收。入口切换不能把旧响应写入另一个任务。确认使用现有交互即可，不要求额外弹窗。

“处理资产差异”仍不足以交给实现者：若仅查询、展示或编辑客户端输入，可属于准备；若产生业务写入，必须明确该操作的输入输出、确认和真实回执，不能藏在完成准备中。多次写入分别保留结果，不假定跨请求事务、撤销、补偿或自动重试。具体采用哪种处理依 A2 确认。

`VisitStartRequirements` 也需修正：禁访结论不能被迫携带位置配置，配置缺失不能补零或默认坐标。准入结论与配置可用性分别表达，例如保留 `admission`，将位置部分改为 `{ kind: 'available', destination, departureRangeMeters, arrivalRangeMeters } | { kind: 'unavailable' }`。已知禁访仍是禁访，已知允许但配置缺失也不能丢失这两个独立事实；后续行为依据真实业务约定。该契约服务开始场景，不自动成为完成场景的条件。

适配器负责校验原始响应并按已确认码表解释业务 `code`，保留请求关联和原始码用于诊断；消费者使用功能语义结果。HTTP 成功、返回任务 ID、类型编译通过都不能证明业务完成。超时或缺码不能推断确定失败；成功码可信但回执损坏时不能当普通失败再次提交。用户可见提示使用简体中文，原始异常不得直接透传。

必要验证范围：

- **真实功能与适配器：** 客户到任务定位的零、一、多候选；完整与不完整覆盖；查询失败；客户与任务不匹配；业务码及必要回执校验。断言完成链路从不创建任务、未取得有效引用时不提交。
- **共用场景与接线：** 手动和聊天进入同一完成流程；任务选择、确认取消、内容变更、提交重复触发、任务切换后异步回执归属；差异处理若写入，验证确认和部分成功的真实展示。验证开始条件变化及其实际消费者，防止破坏既有开始流程。
- **模型评测：** “完成统一便利店的拜访”等表达正确产生客户查询条件；同名、未知客户及必要澄清；不伪造任务 ID。若任务识别或装配共享逻辑受影响，补相关切换、复合意图样本。模拟输出只证明 Portal 接线。
- **业务联调：** 核实查询覆盖、真实任务身份、原始码表、完成权限和规则、资产差异处理及最终业务事实。只有实际涉及设备操作或设备配置行为变化时，才补相应设备场景和真机验证。发布仍执行现有 required 检查。

待确认项仅记录未定业务事实，不阻断其他已明确部分的评审：

- **A1：** 可查询任务的日期、计划与分页覆盖；客户到任务的实际接口及候选含义。确认后同步任务查找契约和验收，不能从旧代码推导业务规则。
- **A2：** 完成条件、必要提交字段、资产差异是否写入及其确认责任；各相关接口码表、必要回执与实际可用的结果核实能力。
- **A3：** 开始条件中准入未知、位置配置不可用时的业务处理及外部数据约定。先保留真实状态，不猜测允许继续或禁止继续的规则。

## B. 照片适配的小改动

**保留字段适配，删除顺带添加的两次重试和缺码兜底成功。** 修改限制在 `visitPhotoAdapter` 的原始响应校验与映射：已确认的数值 `code: 200` 且 `data.objectUrl` 满足接口数据契约时，映射为原有 `{ uri }`。公共成功结果和 `uploadBinary` 保持不变，无需新增公共抽象或通用转换机制。

字符串 `"200"`、HTTP 200、单独存在 `objectUrl` 均不能代替业务成功码。原始输入按 `unknown` 校验；缺码、未知码及写入超时保留结果无法确认的含义，已知业务失败按失败处理；成功码可信但必要 URL 回执异常时保留成功证据，不能归为可随意重试的普通失败。使用既有结果或异常通道表达这些语义，适配器负责中文交互需要的语义映射，不把后端信封暴露给场景。本次不增加自动重试。

验证使用真实适配器并替换上传边界，优先更新现有测试。至少覆盖新字段成功映射、数值与字符串码区别、缺码但有 URL、明确业务失败、未知码、成功码但回执缺失或类型异常、上传失败；断言失败路径不返回成功 `uri`，且上传调用不会被新增重试。不能只断言一条成功路径的 `uri`。

定向范围为适配器契约测试及店头照、自拍照两个直接消费者的现有相关回归与接线检查。H5、问卷没有调用该适配器，本次无需仅因共用 `uploadBinary` 而扩大到它们；CI 发布 required 检查仍按现有配置执行。以后每次按实际依赖和语义变化重新确定范围，不能固定为“永远只跑此适配测试”；若修改上传取消或资源释放语义，应重新纳入相关消费者。

## C. 普通内部调整

**按已有授权完成，无需追加设计审批。** 将两段等价整理逻辑抽为模块私有普通函数，保持调用位置和行为，公共接口不变。不新增公共模块、状态、配置机制或专门设计文档，也无需为纯抽取重复编写测试。

实施后检查差异只包含函数抽取与两处调用替换，运行现有真实适配测试，确认两段分支及原有行为断言通过，并执行该变更需要的既有静态检查。定向范围留在客户查询适配及实际受影响部分；没有依据扩大到全领域、模型评测或真机测试。进入合并或发布阶段时继续遵守现有 required 门禁。
