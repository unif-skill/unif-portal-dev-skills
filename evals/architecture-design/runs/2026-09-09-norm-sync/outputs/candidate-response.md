设计结论：保留后端原始契约对完整数据的定义；展示层另用允许嵌套字段缺失的读取视图。接口结果由各端点已确认的业务码决定，展示完整性与下一步写入所需输入分别判断。依据是指定平台规范第 6.1—6.3 节、第 6.4 节及第 7 节；规范来源为 `unif-platform-architecture/ARCHITECTURE.md`，源 SHA-256 为 `1a6c8eb93a1763517acbfa1acbf0e8e9eba4ddfda83f760985c95bdc84bea458`。

草案需要调整的部分如下：

- 后端原始类型按接口应提供的完整内容定义，这一点成立。不能把它同时当作读取视图，并用完整对象 Schema 的失败来拒绝整页、删除缺值行或增加异常计数。接收边界仍需要校验业务码并安全读取字段，但不以数据完整性增加第二道接口成功门槛。
- “字段缺失仍展示”成立，但只让 `task`、`customer`、`address` 可选不足以表达实际数据：它们存在时，内部字段仍可能缺失。必须让读取视图中的这些嵌套字段也可选，并保留数组中的 `null` 条目及其位置。
- 缺少列表不能统一转为空数组。实际 `[]` 表示本页无记录；没有可读取的列表仅表示“暂无列表数据”，不能推断业务无匹配。
- 列表索引不能填作 `visitTaskId`、`customerId` 或其他业务身份。展示允许缺项，写入必须使用实际取得的必要输入；缺少输入的行仍展示，但当前不能提交完成拜访。
- 删除 `success_receipt_invalid` 和自动再次创建。已确认成功码下，缺少编号用可选字段表达，仍是创建接口成功。编号缺失仅阻止依赖真实编号的详情读取，不能推翻成功结果，也不能据此重复写入。
- 公共传输层只负责传输、认证等技术事项。营销端点的数值 `200`、数值 `403` 与另一个领域的字符串 `"OK"` 分别由对应适配器解释，不统一成功码、不擅自转换码类型。页面与场景消费映射后的结果，不再各自解析原始业务码。

最小 TypeScript 设计示例如下。这些是本题的读取视图和功能输入设计，不是新增后端 API；原始协议类型仍留在适配边界。

```ts
interface TaskView {
  visitTaskId?: string;
  phase?: string;
}

interface CustomerView {
  customerId?: string;
  customerName?: string;
}

interface AddressView {
  city?: string;

}

interface TaskRow {
  task?: TaskView;
  customer?: CustomerView;
  address?: AddressView;
}

interface TaskQuerySuccess {
  status: "success";
  // 有列表时保留全部条目和顺序；undefined 表示无可读取列表。
  items?: Array<TaskRow | null>;
}

interface CompleteVisitInput {
  visitTaskId: string;
  customerId: string;
}

interface SaveReasonInput extends CompleteVisitInput {
  reasonId: string;
}

interface SaveReasonSuccess {
  status: "success";
  // 由此端点已确认的 data === true 条件映射。
  canContinue: boolean;

  id?: string;
}
```

成功接口示例不是所有结果分支的完整声明。权限拒绝、传输失败和结果未确认仍需按功能需要分别表达，不能塞进这些成功接口。也无需为了本次调整引入通用结果转换引擎。TypeScript 必填字符串不能证明业务身份真实；构造写入输入时，场景仍要检查实际数据来源和必要字段，不能通过类型断言、空字符串或索引补齐。缺少身份数据的获取方式未在题设中提供，因此不补造查询、创建或恢复接口。

逐个响应按以下方式处理，各响应彼此独立：

| 响应 | 接口结果与展示 | 后续处理 |
|---|---|---|
| 1：`code: 200`，三条列表项 | 查询成功，保留三条及原顺序。第一条展示状态为空、客户名为空、地址为杭州；第二条展示状态 `visiting` 所对应的既有展示、客户名店乙、地址二号路；第三条 `null` 保留位置，各展示字段为空。不新增状态翻译或状态业务规则。 | 第一条实际包含 `V1`、`C1`，可为后续写入提供身份输入，但不因查询成功自动提交。第二条和第三条缺少必要身份，点击后不能构造合法完成输入；需要保存原因时还必须取得用户选择的 `reasonId`。 |
| 2a：`code: 200`，`items: []` | 查询成功，读取视图为 `items: []`，展示本页无记录。 | 不扩大为所有页面、所有业务均无匹配。 |
| 2b：`code: 200`，`data: {}` | 查询成功，读取视图不提供 `items`，展示“暂无列表数据”。 | 不伪造空数组，不推断业务无匹配。 |
| 3：保存原因 `code: 200, data: false` | 保存原因接口成功；映射为 `canContinue: false`。 | 此端点只有 `data === true` 才允许继续，因此停止后续完成拜访请求。界面区分“保存原因接口成功”和“尚不满足继续完成拜访的条件”，不报为保存接口失败。 |
| 4：创建 `code: 200, data: {}` | 创建接口成功，`id` 缺失。 | 展示创建成功及暂缺详情所需编号，不调用需要真实编号的详情读取，不另设回执异常结果，不自动再创建。题设没有提供核实编号的能力，不能假定存在。 |
| 5a：查询无 `code`，有空数组 | 缺少判断接口成功的依据，查询结果未确认。 | 不把 `items: []` 展示成已确认的“本页无记录”。 |
| 5b：写请求超时 | 写入结果未确认，不能断定成功，也不能断定业务未执行。 | 保留所属请求的必要关联，提示“操作结果未确认”；未有重试、幂等或核实能力的契约依据，不自动重提或补造核实接口。 |
| 5c：营销写响应 `code: "200"`，含 `id: "N1"` | 字符串码未确认，写入结果未确认。 | 不转成数值 `200`，不以编号证明成功，不作为已确认成功继续推进。 |
| 6：另一个领域 `code: "OK", data: 0` | 对应适配器按已确认码表判定查询成功，统计值保留为 `0`。 | 正常展示零；不能用 `if (!data)` 把它判为失败或缺数据。 |

营销端点如返回数值 `403`，按已确认的权限拒绝处理。其他码值没有已确认含义，不能一概当作明确业务失败，更不能猜测成功。原始码和必要请求关联保留在所属请求的解释与诊断记录中；消费者使用语义结果，用户文案使用简体中文。

调用边界保持简单：查询功能负责读取与映射，页面负责展示；点击进入所属场景后，场景准备实际身份输入、用户选择及已有确认依据，再调用保存原因或完成拜访功能。保存原因是写操作，不能隐藏为普通查询准备。若走保存原因后继续完成的链路，只有保存接口成功且 `canContinue` 为 `true`，并具备完成所需输入和确认，才进入完成步骤；两步各自保留真实结果，不宣称跨请求原子事务。查询快照不替代业务系统提交时的规则与权限校验。

选择、待提交内容和确认由 Portal 场景维护；点击列表本身在本题只表示开始准备，不能推成提交授权。已有明确表达提交内容和副作用的动作可以承担确认，不重复询问；内容变化时按具体提交内容重新核对确认。取消准备停止后续调用；写请求已发出后取消等待不表示业务撤销，迟到响应仍归属于原请求和交互。普通函数、参数、返回值和局部状态足以支撑这里的读取、输入检查及步骤协调，无需新增公共状态中心或关联协议。

必要验收应覆盖以下行为；这是设计验收范围，未声称已经执行测试：

1. 对真实查询适配逻辑替换网络边界，输入响应 1，验证成功结果包含原顺序的三项，第一、二项可表达嵌套缺字段，第三项仍保留；页面逐字段空显示，没有删行、整页拒绝或异常计数。
2. 分别输入 `items: []` 与没有 `items` 的成功响应，验证读取视图和中文展示能区分“本页无记录”与“暂无列表数据”。
3. 在真实场景逻辑中验证第一条使用实际 `V1`、`C1` 构造输入；第二、三条缺身份时没有写请求。缺少用户选择的 `reasonId` 时没有保存原因请求；任何提交都不使用索引、空占位值或臆造身份。
4. 保存原因返回 `200/false` 时，断言接口成功且不发送完成请求；补 `200/true` 样本验证该条件允许继续，并仍要求完成输入与确认齐备。不能让假值改判接口失败，也不能让成功码绕过业务条件。
5. 创建返回 `200/{}` 时，断言创建成功且编号可缺失，创建调用总次数仍为一次，没有依赖虚构编号的详情请求，也没有 `success_receipt_invalid` 结果。
6. 覆盖营销数值 `200`、数值 `403`、缺码、未知码、字符串 `"200"`、写超时，以及另一领域的 `"OK"/0`。断言对应结果语义、零值展示、未确认写入不自动重提；即使有编号或 HTTP 成功也不能覆盖业务码判断。
7. 核对受影响的读取视图生产方、列表消费者、写入输入构造处及保存原因到完成的组合链路，进行类型与契约验证；类型、运行时读取规则和需要的 Schema 保持各自契约内同源。若修改了公共传输代码，补查另一个领域等实际消费者，验证业务码解释仍在各适配器。影响不明时扩大到相关领域及集成链路。
