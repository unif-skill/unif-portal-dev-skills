# 推荐设计

依据附带平台架构快照（源 SHA-256：`0dd53bb3a432383c8af3e108552cc1ca47293b7d74aa655edbac67e8e5e20484`）。以下接口名和字段组合均为设计候选，正式名称和外部接口映射需由领域契约确认。

营销保留一个领域智能体，拜访、下单分别维护任务指令、输入输出契约和评测。普通代码承担入口转换、上下文装配、转发、查询、场景推进及结果展示。明确领域和任务的请求直接选取相应内容，不增加独立模型路由；每轮只装配必要任务、引用和上下文。模型仅承担必要理解、参数提取和澄清。

## 必要契约与状态

| 交接 | 必要内容及约束 |
|---|---|
| Portal → Agent：理解请求 | 请求关联、所属交互关联、用户原文、领域及任务线索、必要实体引用。存在草稿时才带相关片段；本题首轮没有订单草稿，不伪造草稿 ID。 |
| Agent → Portal：理解结果 | 同一请求关联；分为类型化意图、必要澄清、受限数据需求。每个分支携带本任务必需的参数；意图不能代替确认或业务成功。 |
| Agent → Portal：商品数据需求 | 所属请求、查询条件和继续理解需要的字段及数量范围。Portal 校验需求并在允许范围内执行，不接受任意模型指定的业务访问。 |
| Portal → Agent：续交接 | 原请求关联及本次数据需求关联、受限候选投影和范围说明，或明确查询失败。有限候选不能被视为完整商品集合。 |
| 客户查询功能 | 输入为明确查询条件；输出为类型化列表及契约实际提供的范围信息，或明确错误。只读、不替代用户选择、不产生业务写入。 |
| Portal 场景 → 业务操作 | 明确客户、准备完整的具体提交内容及本场景有效确认依据；业务操作通过适配器构造原始请求。 |

契约类型、边界运行时校验和模型 Schema 保持同源。引用校验及查询投影保留为所属模块内部普通函数，不为本题新建通用状态中心或转换引擎。

发话时，Portal 将本轮“这家店”所指的 A 作为明确引用固定到请求及其所属交互。跨拜访转入下单，通过类型化输入显式传递 A；订单场景接收后维护自己的客户与草稿。拜访客户、列表选择和订单客户分别归属各自交互，不共享一个可变的 `selectedCustomer` 对象。

列表随后选中 B，只改变列表交互。模型迟到结果按原请求返回，Portal 校验请求关联和引用，仍将订单意图接入 A 的订单交互；不能读取此刻的 B 来填充订单。若模型返回与请求 A 冲突的引用，拒绝应用该结果并按所属交互处理异常或澄清。若原交互已取消或失效，不用迟到理解结果推进后续写入，更不能更新 B 的任务。结果是否立即打开 A 的订单界面属于待确认的呈现选择，不影响订单归属。

“给这家店下两箱商品甲”产生针对 A 的下单意图，包含商品甲这一待解析商品表达、数量 2 和原文单位“箱”；未确认的商品身份和单位换算不猜测。Portal 必要时查询并协助澄清，形成 A 的草稿，再走订单场景既有的准备、确认和提交。确认绑定具体客户和提交内容；内容改变后，旧确认不能继续授权不同内容。模型输出本身不构成提交确认。

## 多入口调用过程

普通客户查询框：表单条件 → 同一客户查询功能 → 适配器 → 业务系统 → 类型化查询结果 → 列表直接展示。查询成功且为空与查询失败分别表达，没有业务写入，也没有模型调用。

自然语言客户查询：用户原文 → 必要的客户查询任务理解 → 类型化条件 → Portal 校验 → 同一客户查询功能 → 列表直接展示。无需将整份列表送回模型，也无需模型再总结。仅在用户任务确实需要继续理解时才发生受限数据续交接。

完成拜访的 AI 入口：完成意图 → Portal 拜访场景；手动按钮：交互事件 → 同一拜访场景。两者共用已确认需要的资产差异处理、确认及最终完成操作。`completeVisit` 若指最终写入功能，只能由场景在准备和确认满足后调用，AI 不直接绕过场景调用。资产差异规则、查询与处理接口、可能产生写入的具体步骤，必须按营销业务契约确认；不能把写入藏入“准备”。设备操作也由 Portal 按场景安排。

## 服务端实际接线

模块图中的“Portal ↔ 营销智能体”表达内容由谁生产和消费，不足以证明 Portal 必须直接连接一个营销部署服务。推荐以超级智能体的服务端入口接收自然语言交接，由其普通协调代码对接领域运行代码；领域明确时，超级智能体模型无需参与。入口与运行代码可同进程，也可分部署，分仓本身不决定服务数量。

下面 `──网络──>` 表示跨已知系统边界的传输；`──普通调用──>` 表示不调用模型的协调动作。服务端内部是否进一步跨网络，取决于待确认的部署方案，不能由这些逻辑组件名称推断。

### 首轮请求

```text
Portal（原文、请求关联、营销/下单线索、A 引用）
  ──网络──> 超级智能体服务端入口 / 普通协调代码
  ──普通调用──> 营销运行代码（装配通用指令 + 下单任务及必要契约）
  ──模型调用──> 营销模型
```

此轮领域、下单任务已明确，模型调用发生在营销理解处。普通校验、路由选择和转发不生成模型 Token；如果实现主动调用了模型做这些事，才增加相应模型调用成本。

### 必要数据续交接

```text
营销模型生成类型化商品数据需求
  → 营销运行代码
  → 超级智能体服务端入口 / 普通协调代码
  ──网络──> Portal 校验需求及请求归属
  → 同一商品查询功能 → 业务适配器
  ──网络──> 业务系统
  ──网络──> Portal 接收并解释查询结果
  → Portal 生成受限候选投影，保持 A 和原请求关联
  ──网络──> 超级智能体服务端入口 / 普通协调代码
  → 营销运行代码校验续交接并装配必要候选
  ──模型调用──> 营销模型继续理解
```

候选的内容生产方是 Portal，消费方是营销理解任务；实际传输仍经服务端入口和运行代码，不需要 Portal 直接连接营销模型或泄露业务认证信息。Agent 不直接查询现有业务系统。若候选无需进一步推理，Portal 直接继续交互，不强制产生这一模型续调用。

### 类型化结果返回

```text
营销模型生成类型化理解结果
  → 营销运行代码校验
  → 超级智能体服务端入口 / 普通协调代码按原请求返回
  ──网络──> Portal 校验结构、引用和交互关联
  → A 的订单场景 → 准备与确认 → 订单业务操作
  ──网络──> 业务系统最终校验并写入
  ──网络──> Portal 适配器解释业务码 → 所属订单交互展示
```

不再调用超级智能体模型生成“统一总结”。Portal 可依据类型化结果显示中文提示，并以代码记录必要结构化结果。领域理解成功与订单业务成功是不同结论；后者必须由适配器依据实际接口的业务 `code` 解释，HTTP 成功或模型文字不能作为依据。写入结果未确认、业务拒绝、业务成功但必要回执异常需按真实外部契约区分，不能统一按失败重试。取消等待不代表业务撤销，后续回执仍归属原请求。

这些路径是推荐接线，尚未证明真实系统已如此连接。落地时要把入口端点、进程内调用或内部网络调用、认证边界及跨部署版本约束落实到具体部署方案。

## 后续输入与公用记忆

页面仍在订单且 `taskHint` 仍为下单时，“另外，帮我查设备报修进度”表达了新的领域请求。`taskHint` 只是线索，不能把该输入锁在营销任务。服务端按领域目录识别到设备运维并交接该领域；已有明确结构化依据时由代码转发，需要自然语言判断时才使用必要的领域识别模型调用。随后装配设备运维所需任务内容，不继续加载营销下单任务，不修改原订单草稿。报修对象、查询条件不足时，在新任务中澄清，业务查询仍由 Portal 对应查询功能发起。

对“那个现在怎么样了”，题设已明确当前引用无法消歧，应返回中文澄清以确定所指对象或任务。不能因页面、旧 `taskHint` 或历史记忆擅自选定订单或报修，也不据此发起写入。澄清和必要识别可能增加模型调用，不承诺所有请求一次理解完成。

营销运行代码可以按实际需要直接通过现有公开记忆契约检索商品简称线索，不穿透记忆服务内部实现，也不要求超级智能体代理。逻辑调用是“营销运行代码 → 公用记忆服务公开契约 → 营销运行代码”；物理上是否跨网络由记忆部署决定，检索与转发本身不等于模型调用。本题不新增记忆写入、公共缓存或新代理接口。

只取与商品甲解析相关的必要线索，保留公开契约实际提供的来源和范围语义，按需提供给本次任务；不缓存整个领域记忆并每轮灌入系统指令。记忆中的旧客户不能覆盖 Portal 本轮明确的 A，历史线索也不能升级为当前商品身份、当前查询事实或业务提交依据。无命中或记忆读取失败不伪造线索；依据实际契约继续处理必要查询或澄清。

## 必要验证与待确认项

以下均为计划验证，未执行产品测试、模型评测或联调。

- **任务评测**：分别验证拜访、下单及自然语言客户查询的意图、参数、单位、引用和澄清；覆盖 A 发话后列表切 B、错误客户引用、无草稿的跨任务承接、旧任务线索下转设备运维、“那个”的歧义、相关记忆命中及旧客户冲突。结构合法、语义准确、业务合法分别判断。单任务调整验证该任务和相关切换样本；通用指令、共享契约或装配方式变化扩大到受影响任务。
- **功能及场景验证**：测试真实客户与商品查询功能，替换外部网络，覆盖成功、有效空结果和失败；验证两种查询入口调用同一功能且无写入。用可控模型结果验证手动和 AI 完成拜访共用资产差异处理、确认及提交链路；确认不满足或交互取消时无提交。覆盖 A/B 并发交互、迟到结果、内容变化后的确认失效，以及业务码映射、未确认结果和异常回执。
- **接线验证**：在实际组装入口记录请求关联和调用轨迹，验证首轮、数据需求回程、候选续交接及类型化结果回程均接入真实依赖；确认业务查询由 Portal 发起。分别统计普通转发、实际模型调用，检查明确营销请求未额外调用路由和总结模型，限制候选字段与数量，核对领域切换及直接使用公用记忆契约的接线。模型替身可以证明协调顺序，不能证明真实理解质量。
- **影响与集成**：识别两类入口、拜访和订单场景、查询功能、服务端协调代码、两个相关领域及记忆契约的实际生产方和消费者。原始业务接口码表、权限及最终事实通过实际业务系统联调确认；若资产处理涉及原生能力，再补对应真机验证。合并发布遵循实际 required CI；影响范围不明时扩大到相关领域与集成链路。
- **效果测量**：相同业务行为下，统计一次目标的全部路由、澄清、理解和续推理调用数、累计输入输出 Token 与端到端延迟，区分系统处理和用户等待。当前没有用量数据，成本及延迟降幅未知。

需确认的具体缺口为：营销任务和功能的正式契约；资产差异处理步骤及写入副作用；订单单位与商品身份解析规则；业务系统原始码表及结果核实能力；请求与交互的失效规则及迟到 A 订单的界面呈现；服务端部署宿主、入口端点、内部接线及版本兼容范围；设备运维查询所需引用和公开结果契约；现有记忆公开契约的检索范围、错误语义和可用来源信息。上述缺口不改变已经确定的 A 归属、多入口共用场景及普通转发无需模型的职责划分。
