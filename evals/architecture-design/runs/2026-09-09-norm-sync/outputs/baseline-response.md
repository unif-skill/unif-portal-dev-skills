草案应拆开三个判断：接口是否成功、数据能否用于读取展示、当前输入能否用于业务写入。三者使用不同依据，不能用同一份完整对象 Schema 合并判断。

依据所附平台规范第 6.1—6.3 节，后端原始契约、功能读取视图和写入输入各自表达边界；成功码由对应业务适配器解释。字段投影、结果映射和输入检查保留为普通函数，本题没有新增公共转换框架或独立能力的必要。

后端原始类型继续如实描述其应提供的完整数据；实际网络输入仍从 `unknown` 开始检查，不能直接断言为完整类型。读取视图只保留展示和后续交接需要的字段，并允许这些字段缺失。写入输入则要求具备题设规定的真实身份，保存原因还要求用户选择的原因。

最小类型示例为：

```ts
// 功能读取视图：外层对象和内部字段都允许缺失。
interface TaskRow {
  task?: {
    visitTaskId?: string;
    phase?: string;
  };
  customer?: {
    customerId?: string;
    customerName?: string;
  };
  address?: {
    city?: string;
    street?: string;
  };
}

// null 单独表达无法投影为任务行的原始项，不能冒充 TaskRow。
// 仅在已确认 items 为数组后构造该读取结果。
interface TaskListData {
  items: Array<TaskRow | null>;
}

interface CompleteVisitInput {
  visitTaskId: string;
  customerId: string;
}

interface SaveReasonInput extends CompleteVisitInput {
  reasonId: string;
}
```

这些是设计示例，类型和运行时检查在实现时应保持同源。`string` 类型本身不能证明 ID 来自真实业务实体，也不能证明原因经过用户选择；场景必须在构造写入输入时检查来源与缺失情况。不能用列表索引、随机值或类型断言补齐身份。展示需要的名称、状态和地址不因此变成写入必填项。

只把 `task`、`customer` 和 `address` 设为可选并不够：例如 `task` 存在但只有 `visitTaskId` 时，原草案仍要求 `phase`；第二行的 `customer` 存在但缺少 `customerId`，同样不满足原类型。应逐层表达实际读取容忍度，不能用“字段缺失仍展示”的文字代替契约调整。题设未说明叶子字段可为 `null`，不把所有字段一律扩成任意可空类型。

逐个响应的处理如下：

| 响应 | 接口判定与读取结果 | 后续处理 |
|---|---|---|
| 1：`code: 200`，包含两条不完整对象和一个 `null` | 已有接口成功依据。两条对象按读取视图保留已有字段，不因不满足完整后端 Schema 而移除。第一条保留 `V1`、`C1`、杭州；第二条保留 `visiting`、店乙、二号路。缺失展示字段如实表达缺失，不推导客户名或任务状态。`null` 是无有效行内容的项，单独保留其不可读取性质，不转换成正常任务或写入输入。 | 第一条具备完成拜访所需两个 ID，可以在点击后进入输入准备；它仍须遵循场景的提交确认，业务系统最终校验。第二条和 `null` 无法构造写入输入，不发送完成请求。若需保存原因，第一条也必须先取得用户选择的 `reasonId`。题设没有补查能力，不新增补查或创建请求来补齐身份。 |
| 2a：`code: 200, data: { items: [] }` | 查询成功，且明确没有结果。 | 可以进入列表空态。 |
| 2b：`code: 200, data: {}` | 保留成功码证据，但缺少读取列表所需的 `items`，无法得到有效列表结果。 | 表达列表响应异常，不能补成 `[]` 或声称没有任务。它不是业务码拒绝。 |
| 3：保存原因得到 `code: 200, data: false` | 保存原因接口成功；`false` 是题设允许且有明确业务意义的结果。 | 继续条件不满足，停止后续完成拜访调用。不能把它当传输失败，也不能因为接口成功就继续。功能结果需携带这一条件的真实值，场景仅在 `data === true` 对应的语义成立时继续。 |
| 4：已发送创建得到 `code: 200, data: {}` | 创建存在可信成功码，但缺少后续读取详情必需的真实编号。 | 区分“业务成功但回执异常”，保留请求关联及成功码证据；不调用需要编号的详情读取，也不自动再次创建。 |
| 5a：查询只有 `data: { items: [] }` | 缺少业务码，无法确认接口成功。 | 表达查询结果未确认或响应缺码，不能按成功空列表展示。 |
| 5b：写请求超时 | 无法确认写入是否发生。 | 表达写入结果未确认，保留请求关联；不能推断确定失败或自动重发。 |
| 5c：写响应 `code: "200", data: { id: "N1" }` | 营销契约只确认数值 `200`，字符串 `"200"` 的含义未确认。编号存在不能代替成功码。 | 结果未确认，不强转码值，不把 `N1` 当作创建成功的证据，也不据此继续成功分支或自动重发。 |
| 6：另一领域 `code: "OK", data: 0` | 该领域已明确字符串 `"OK"` 成功，且 `0` 是有效统计值。 | 返回成功统计结果并展示 `0`，不能用真值判断把它判为失败。 |

数值 `403` 是营销端点明确的权限拒绝，应映射为业务拒绝并展示相应中文说明；其他未确认码值保留未知性质，不扩写码表。公共传输层统一只接受数值 `200` 的方案应删除：传输层负责网络与认证等技术事项，营销与另一领域分别在各自适配器解释已确认码表，页面和场景消费语义结果。

整页套用完整对象 Schema 并删除缺值行会丢失可展示数据，也把展示门槛错误地等同于写入门槛，应改为信封、列表容器及实际消费字段的必要检查与投影。缺失叶子字段与 `null` 行项要分开处理：前者仍是可展示的部分记录，后者不能构成任务记录；不能把两者合并为一类删除，再用异常计数补偿信息损失。题设没有异常计数的产品要求，无需新增计数契约或界面行为。必要的原始异常和请求关联可以保留于请求诊断中。

`success_receipt_invalid` 作为创建功能区分“成功但回执异常”的候选状态名成立，其依据是规范第 6.2 节明确要求保留这一差异；它不能归入允许普通失败重试的分支，更不能成为再创建一次的触发器。显示文案应表达“创建已返回成功，但缺少记录编号，暂时无法读取详情”，而不是显示创建失败。题设未提供核实、幂等或恢复接口，不能承诺自动恢复。

场景负责点击后的输入准备、原因选择、提交确认和调用顺序。保存原因是有业务写入副作用的操作，不能隐藏为只读准备。确认由 Portal 对应交互维护，并绑定实际提交的任务、客户和原因；不额外假定需要一个新弹窗。保存原因成功但继续条件不满足时，保留这一步真实结果，不能声称整个流程已完成。请求发送后取消等待不等于业务撤销，迟到结果仍归属于原请求及原交互，不能写入其他任务。

必要验收应覆盖真实适配和场景逻辑，替换网络边界；以下为计划验收，未声称已经执行：

- 读取映射覆盖题设第一组数据：两条缺字段对象都保留已知内容，嵌套字段缺失不导致整页失败；`null` 不被当作可提交任务。分别验证成功空数组与缺少 `items`，后者不进入空态。
- 写入准备验证第一条的真实 `V1`、`C1` 可以构造输入；第二条及 `null` 不发送写请求，不使用索引补 ID。保存原因缺少用户选择的 `reasonId` 时也不发送请求。缺少仅用于展示的名称或地址不额外阻止具备必要 ID 的输入准备。
- 保存原因分别验证 `data === true` 和 `data === false`，断言 `false` 保留接口成功语义且完成拜访调用次数为零；`true` 只满足题设规定的继续条件，后续仍以完成请求自身结果判定是否完成。
- 创建成功缺编号时，断言保留成功证据、详情调用次数为零、再次创建次数为零；超时和字符串 `"200"` 的写结果保持未确认，不自动重发。缺码查询不能显示“没有结果”。
- 营销适配器验证数值 `200`、数值 `403`、未确认码值和码值类型；另一领域适配器验证 `"OK"` 与统计值 `0`，证明公共传输层未施加营销码表。检查页面实际中文表达能区分空结果、权限拒绝、响应异常、继续条件不满足和写入结果未确认。
- 影响范围包括读取视图的列表消费者、写入输入的准备逻辑、保存原因与完成拜访的组合链路、创建回执的详情消费者。若实际修改公共传输代码，扩大到受影响领域适配器与其接线；没有真实接口和产品实现，本次不能声称已完成联调、CI 或业务事实验证。
