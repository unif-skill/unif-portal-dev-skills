# 人工判定规则

评测者阅读实际产出，不以标题、关键词或复述条款作为通过依据。以下内容不提供给被测模型。设计结论测试不能证明生产代码和运行时理解已经正确。

方法名本身不是固定判据。依据职责、输入输出、副作用、调用关系及材料来源评分；正式契约中的名称应保持一致，其他候选应说明草案性质。题设的“实际关系”“已在使用”不升级为真实源码证据。准确引用、比较和反例中出现旧名称不算污染，不因字符串相同或不同直接判错。

## review 样本：六项分别评分

- A1：发现仅客户引用到任务引用的只读交接缺口；先核对已有契约，必要时提出只读发现候选，不用任何可能创建任务的操作代替完成前的只读定位。名称变化不改变此判断。
- A2：覆盖零、一、多任务与查询范围不完整；不猜日期、自动取最新、截断后当唯一或凭空新增既定业务筛选。
- A3：允许 blocked / unknown 在没有位置和阈值时被准确表达；不要求占位坐标或零阈值。
- B1：按既定 code 与字段映射保留公共契约，不以 URL/HTTP 成功代替业务成功；本次不实现未经要求的重试。
- B2：本次验证真实适配、码与映射、必要消费者；不承诺所有后续变化只测一个文件。公共上传语义变化时扩大真实消费者，发布 required 保留。
- C1：正常内部重构沿用已有授权和有效测试；不强制新增公共模块、固定设计模板、重复测试或再等一次批准。

完整通过需要六项均满足；只写“需遵守架构”而无可执行结论按对应项未满足。记录原文证据及不确定评分原因。允许接口命名与设计形式不同。

## switch 样本：七项分别评分

- S1：A 引用随本次交互捕获，迟到响应不改用 B；订单和拜访分别拥有状态。
- S2：普通聊天由超级智能体理解，自答或按完整语义选择唯一营销助手中的 order、visit、customer 或 marketing；taskHint 或已知领域不等于显式 skill，不能单凭它跳过路由。单一任务只装配对应片段，跨任务或营销范围不确定保留完整 marketing，不按关键词裁剪。全输入显式 order 且非重新生成时按契约直接委派。普通查询与类型化有限问卷沿原入口，不增加聊天或路由回合；指令、代码契约与独立评测关联。
- S3：AI 和手动完成进入同一 Portal 场景，确认和资产步骤不由入口重复维护。
- S4：普通查询共用核心且直接展示，不将整份列表或无关历史自动送回模型；只在必要续推理时提供受限数据。
- S5：首轮自然语言输入、必要续推理数据和领域结果均经超级智能体服务端入口交接；委派保留原输入、任务线索、附件和必要上下文，运行代码验证允许的委派和来源。模块双向箭头只表示内容关系，分仓不直接决定部署；供数不重复路由，领域结果不经超级模型改写或总结。
- S6：普通常识由超级智能体自答；设备报修输入不因旧 taskHint 被当作下单，不编造未接入的助手、业务契约或结果；含糊指代按本轮信息澄清。自答通常一次、委派通常两次模型调用，普通转发无模型调用或模型 Token，必要续推理按实际计，未知用量不填零，不宣称已测得成本下降。
- S7：记忆按需要由营销运行代码直接调用公用服务，先做访问与适用范围过滤、再限制条目字段；记忆是有来源的线索，不覆盖本轮 A 引用或成为另一份草稿，不将全量记忆放入系统指令。

## task-routing 样本：五项分别判定

- T1：全输入显式 skill=order 且非重新生成时，Agent 运行代码直接委派 order，保留认证、来源、附件、轮次和取消；不把 taskHint 等同显式声明。
- T2：两项普通聊天分别由原路由模型选择 visit、customer，只装配对应业务指令及同源投影；跨任务组合选择完整 marketing，不增加任务选择模型或关键词分派。
- T3：复合动作保留真实来源、客户关联和用户明确的先后关系；Portal 承担实际执行、草稿和确认，加商品不等于提交订单。
- T4：追加未标记的输入后重新判断完整有序集合，不继承旧 skill、不受旧 taskHint 锁定；旧调用和路由失效，迟到结果不能被新输入采用。同一输入版本的合法供数沿原任务继续，不重新路由。
- T5：固定分析不进入聊天路由，普通回复重新生成沿原回答者且仅允许回复，不恢复业务查询或动作；普通列表翻页不调用模型。模型次数按实际路径，未运行的费用与时延不声称改善。

这是当前版本维护样本。先固定相同输入、模型、推理档位和读取权限，分别在独立上下文使用旧包与同步后的包；判据不交给被测上下文。逐项保留原文证据，基线已满足项只检查回归，不计新增收益；少量设计样本不代表真实业务正确率或自动触发效果。

## response 样本：五项分别评分

- Q1：数值 `200` 下，三条列表记录及顺序保留，缺失的嵌套字段可空展示；不因一条缺值拒绝整页、剔除或计为异常。读取类型的嵌套可选性与该行为一致，不能只将顶层对象设为可选；原始应有数据契约与读取视图分开。
- Q2：真实空数组只证明本页无记录；不存在可读取的列表时保持成功、暂无列表数据，不推断业务无匹配。
- Q3：保存原因的接口成功与 `data === true` 的继续条件分开；创建 `200` 缺编号仍成功，不增加通用回执异常状态、不再次创建，详情操作缺输入时另行处理。
- Q4：写入参数仍要求真实任务和客户身份、相应原因选择；展示空值、列表索引及强制断言不能制造可写引用。手写对象结构使用接口，结果联合由已命名分支组成；以具体类型能否承载题设并约束写入判断，非仅检查关键字。
- Q5：缺码、营销字符串 `"200"` 及未知码不能猜成功，写超时保持未确认；其他领域按自身 `"OK"` 码与有效 `0` 数据处理，不推广营销数值成功码。

## confirmation 样本：四项分别评分

- F1：明确覆盖两张照片、用途和 V1 的选用动作可作为本次保存确认，不逐步骤重复；设备权限不代替业务确认，改变集合、用途或目标时重新确认，保留已成功上传的引用。
- F2：订单确认绑定 D1 第 4 版及实际复核内容，甲的普通查询翻页不使其失效；乙的新编辑输入使旧确认失效且未完成编辑不能按旧确认提交。草稿归 Portal，模型不能提供确认或最终业务事实。
- F3：本批仅适配已确认的字段变化，不把默认首个原因、离线队列、共享草稿等历史或附录内容变成需求；普通函数、真实依赖及局部状态可满足时，不新增全局关联、订阅、重试、补偿或总结回合。既有草稿版本等有契约依据的约束仍保留。
- F4：运行真实 `readReasons` 请求构造、码解释与映射，只替换外部网络等边界；按结果实际影响验证原因选择交接，不因为同文件而一律测全部能力，也不替换被测函数后仅断言预设输出。共享结果或认证等变化、依赖不明时扩大范围，发布 required 不被定向测试替代。

## call-boundaries 样本：四项分别评分

- I1：刷新代码即使收到旧坐标也先调用定位，再以本次客户、新观测和第一页查询；不因缓存或旧观测省略已确认的刷新。
- I2：公共查询的客户、位置、页号来自输入，缺参返回输入错误且不调用外部服务；实际参数和依赖不借用 scene、draft、cache、定位或交互补齐、替换输入或跳过本次查询。
- I3：一次查询只读取指定页，翻页、等待选择与后续确认由对应交互触发并准备输入；方案和代码均不把这些状态机藏进查询。
- I4：验证实际导出的函数及定位、传输的调用次数、顺序和参数，外部依赖可替换；文档中的边界与代码一致，普通内部协调不被强制拆成公共模块。

## 选择技能的边界

应触发：设计独立业务能力；审查新增自然语言入口；修改公共契约及测试影响分析。
不应仅因关键词触发：用户要“开始今天的拜访”；只改按钮颜色；只运行已给定的测试命令；仅准备 PR 标题且无架构改动。

以上判断直接选择架构工作入口；其他阶段确实缺少共同规则时，可以按需取得本技能的相应主题。记录这种资料读取，不将其算作新增架构设计；当前上下文已具备所需正文时不要求重新加载。

## 契约来源与名称变化

- P1：`provenance.md` 项目甲沿用给定的三个正式名称和契约，不因评测出现同名接口而机械改名；已有只读定位能力不重复新建。新入口复用既有完成场景，不调用可能创建的操作。
- P2：不将另一评测中的错误签名、身份交接缺口和依赖设定当作项目甲事实；题设正式契约也不证明真实源码或部署已经接入。按本次接线选择必要验证。
- P3：项目乙基于明确工单引用、关闭说明、确认与关闭职责形成最小候选；新增公开接口标明草案，不宣布其他样本的方法是已有或必建能力，不额外要求从客户发现任务。缺少原始字段和码表时列缺口，不伪造成功依据。
- R1：`rename-a.md`、`rename-b.md` 均识别可能创建操作不能满足完成前的只读定位；说明所缺身份交接和候选性质，保留原开始用途及题设参数、副作用和结果语义。
- R2：两个变体分别独立运行，再比较职责、调用关系、缺口与验证结论。不能因为名称改变而允许创建、增加请求或更换业务目标；允许候选命名及表述不同。

人工逐段判断名称的来源、使用角色和实际行为。正式契约同名、准确引用、比较及反例均不算污染，不按固定字符串出现次数评分。单个成对样本或少量重复不能证明跨模型稳定性、准确性增益或真实源码接入。

## state-identity 样本：五项分别评分

- U1：A 识别正文已同步不能证明日期与默认 ID 的归属已同步，本机缺失不能证明服务端不存在；核对内容、标识、索引、关联及完整身份和业务日期的范围，不把普通台账纳入默认台账唯一性。
- U2：A、B 将唯一性放在所属服务端同一原子查找／创建契约和数据库约束，首页、快捷及批量入口均核实接线；客户端或单进程锁不能替代，超时／失败不生成替代记录。既有真实记录不擅自删并，所需变更超出授权或缺少依赖时明确缺口。
- U3：C 不接受共享映射、固定 ID 替身或仅正文恢复作为跨设备唯一性证据；两个独立客户端具有隔离本地状态，覆盖空／旧缓存、重启、各创建入口、失败不创建及身份隔离，并观察 ID、关联及真实记录数。
- U4：B、C 区分客户端消费者、服务端并发及数据库约束的验证责任；真实服务与数据库验证替身无法证明的唯一性。提出用例不算已经执行，源码、单元、集成及设备证据分别报告。
- U5：D 的圆角调整沿用主题及必要视觉检查；本地偏好修复复用现有存取、验证本机重启恢复，不增加服务端同步、业务唯一约束或全套跨设备测试。

A 至 D 是限定场景，按实际决策与范围判断，不以复述条款或关键词命中判通过；少量候选运行不能证明自动发现、跨模型稳定性或生产业务已修复。

## state-identity E：生命周期交接

- L1：区分已采用事实、协调器等待、资源及 UI；已采用不能因发送方仍等待而回退，采用前中断也不能被冒充成功。取消只收尾仍归本方的执行与资源。
- L2：接收模块的既有流程继续人工补全及回执，不把关闭或等待取消当作业务撤销，不由发送方新造失败流程；真实拒绝或明确撤销按权威结果处理。
- L3：验证真实所有者和消费者，控制采用、中断及回执的先后，核对条目事实、必要副作用与资源释放；迟到结果和关闭／恢复不能改错归属。用例能区分“只保护 Promise 已完成”与“保护已采用但仍等待”，也覆盖未采用及真实业务拒绝，不扩大普通 UI 或纯设备状态范围。

这是新增的单个匿名交接场景，独立记录当前运行，不改写此前 A–D 的冻结输入或评分；题设判断不替代真实工程回归。
