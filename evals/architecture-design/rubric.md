# 人工判定规则

评测者阅读实际产出，不以标题、关键词或复述条款作为通过依据。以下内容不提供给被测模型。设计结论测试不能证明生产代码和运行时理解已经正确。

方法名本身不是固定判据。依据职责、输入输出、副作用、调用关系及材料来源评分；正式契约中的名称应保持一致，其他候选应说明草案性质。题设的“实际关系”“已在使用”不升级为真实源码证据。准确引用、比较和反例中出现旧名称不算污染，不因字符串相同或不同直接判错。

## review 样本：六项分别评分

- A1：发现仅客户引用到任务引用的只读交接缺口；先核对已有契约，必要时提出只读发现候选，不用任何可能创建任务的操作代替完成前的只读定位。名称变化不改变此判断。
- A2：覆盖零、一、多任务与查询范围不完整；不猜日期、自动取最新、截断后当唯一或凭空新增既定业务筛选。
- A3：允许 blocked / unknown 在没有位置和阈值时被准确表达；不要求占位坐标或零阈值。
- B1：按既定 code 与字段映射保留公共契约，不以 URL/HTTP 成功代替业务成功；本次不实现未经要求的重试。
- B2：本次验证真实适配、码与映射、必要消费者；不承诺所有后续变化只测一个文件。公共上传语义变化时扩大真实消费者，发布 required 保留。
- C1：正常内部重构沿用已有授权和有效测试；不强制新增公共模块、固定设计模板、重复测试或再等一次批准。

完整通过需要六项均满足；只写“需遵守架构”而无可执行结论按对应项未满足。记录原文证据及不确定评分原因。允许接口命名与设计形式不同。

## switch 样本：四项分别评分

- S1：A 引用随本次交互捕获，迟到响应不改用 B；订单和拜访分别拥有状态。
- S2：任务明确时不新增路由回合，按任务装配；指令、代码契约与独立评测关联。
- S3：AI 和手动完成进入同一 Portal 场景，确认和资产步骤不由入口重复维护。
- S4：普通查询共用核心且直接展示，不将整份列表或无关历史自动送回模型；只在必要续推理时提供受限数据。

## 选择技能的边界

应触发：设计独立业务能力；审查新增自然语言入口；修改公共契约及测试影响分析。
不应仅因关键词触发：用户要“开始今天的拜访”；只改按钮颜色；只运行已给定的测试命令；仅准备 PR 标题且无架构改动。

## 契约来源与名称变化

- P1：`provenance.md` 项目甲沿用给定的三个正式名称和契约，不因评测出现同名接口而机械改名；已有只读定位能力不重复新建。新入口复用既有完成场景，不调用可能创建的操作。
- P2：不将另一评测中的错误签名、身份交接缺口和依赖设定当作项目甲事实；题设正式契约也不证明真实源码或部署已经接入。按本次接线选择必要验证。
- P3：项目乙基于明确工单引用、关闭说明、确认与关闭职责形成最小候选；新增公开接口标明草案，不宣布其他样本的方法是已有或必建能力，不额外要求从客户发现任务。缺少原始字段和码表时列缺口，不伪造成功依据。
- R1：`rename-a.md`、`rename-b.md` 均识别可能创建操作不能满足完成前的只读定位；说明所缺身份交接和候选性质，保留原开始用途及题设参数、副作用和结果语义。
- R2：两个变体分别独立运行，再比较职责、调用关系、缺口与验证结论。不能因为名称改变而允许创建、增加请求或更换业务目标；允许候选命名及表述不同。

人工逐段判断名称的来源、使用角色和实际行为。正式契约同名、准确引用、比较及反例均不算污染，不按固定字符串出现次数评分。单个成对样本或少量重复不能证明跨模型稳定性、准确性增益或真实源码接入。
