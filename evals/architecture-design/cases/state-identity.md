# 状态与记录归属场景

以下是匿名合成题设，只作只读判断，不操作真实服务、设备或业务记录。题设客户端为 RN，各题按指定研发入口取资料，分别给出本次修改范围、必要实现或验证及证据结论。评估者另读 rubric；被测上下文不读取判据或其他运行输出。

## A：客户端恢复

使用 unif-rn-dev。契约要求一个完整身份（用户、组织、角色）在同一业务日期只有一个默认巡检台账；用户主动新建的普通台账不受此限制。台账正文保存在服务端，两个客户端都能下载。客户端以本地 `date -> ledgerId` 查找默认台账，未命中时生成随机 ID 再请求服务端创建。首页和客户快捷入口各有一段这样的代码。已在设备甲创建默认台账并同步正文，设备乙首次安装后本地映射为空。

当前建议是先刷新乙的正文列表，将本地新建部分加进程内锁，保留两个入口各自实现；如果恢复请求失败则生成一个新 ID 保证进入页面。现有单设备测试都是绿色。请判断该建议是否满足契约，给出最小必要改动边界及未能确认的部分。

## B：后端并发

使用 unif-python-dev。契约要求一个完整身份（用户、组织、角色）在同一业务日期只有一个默认巡检台账；用户主动新建的普通台账不受此限制。按该唯一性契约，后端运行两个独立工作进程。`resolveDefault` 在本进程锁内先按完整身份和日期 SELECT，查不到则 INSERT 随机 ID；表只有 ID 主键，业务键没有约束。另一个批量入口直接 INSERT，客户端超时后可能重新发起请求。普通台账允许同日期多条。

请确定本次服务端调整须到达的调用方、数据约束和最少验证。已有重复台账中可能保存真实内容；本次未授权删除或合并，也未要求新增离线创建能力。

## C：测试与完成判断

使用 unif-rn-test 与 unif-python-test，按各自被测对象选读。报告称默认台账已跨设备同步：正文拉取测试通过；恢复测试中先由同一进程的实例 A 建台账，再由实例 B 恢复，二者共用一个内存映射；后端替身对所有身份与日期固定返回 ID `example-ledger`。没有空缓存、旧关联、进程重启、并发或身份切换记录，也没有数据库约束和多进程执行证据。

请判断当前能证明什么，按实际被测对象与替身边界提出最小补验方案，并说明哪些完成结论仍缺证据。

## D：设备状态与普通 UI

使用 unif-rn-dev。任务一仅将相机手电按钮的圆角从 8 调整为现有主题值，状态和交互保持。任务二另行修复该设备本地保存的预览镜像偏好：重启后应恢复本机选择，产品明确不在账号或设备间共享。两项都已有对应组件和设置存取能力。

分别确定实现与验证范围，以及是否需要服务端接口、数据库约束或两个客户端验证。

## E：接收完成与回执等待

按 unif-rn-dev、unif-python-dev、unif-rn-test、unif-python-test 取得本题实际需要的共同规则。一个导入协调器把校验后的条目交给接收模块。契约允许接收模块先发出“已采用”回调，接收模块负责条目之后的人工补全与远端回执；协调器的调用仍可等待该回执。界面根据条目状态展示进度，重新打开时读取接收模块现有状态。

当前实现：用户关闭发起页或停止等待后，协调器取消自身请求、释放观察器，将所有历史条目统一标记为失败，并尝试发出回退请求；它只用等待 Promise 是否仍未完成判断条目是否结束。已有测试仅断言关闭后 Promise 结束、观察器已释放。题设还包含采用前中断、采用与中断交错、迟到回执、重新打开，以及接收模块返回权威拒绝或用户明确执行撤销的路径。

请决定最小修复范围和必须保留的不变量，指出应该由哪个现有流程继续处理未完成项，并给出能区分错误实现的用例。不要新增工作流引擎或把所有条目都固定成成功。
