# Portal 工程目录与基础代码组织

本文定义 Portal 客户端的目标代码归属、公共入口、基础代码复用和测试组织，供工程初始化、模块开发与代码审查使用。系统职责、业务成功判定、状态归属和模型参与边界遵循[平台架构](ARCHITECTURE.md)；领域内容在各自架构和模块契约中维护。

新增或修改文件时的分类规则、角色文件拆分、变量作用域和命名规范见[Portal 文件开发规则](PORTAL_DEVELOPMENT.md)。

目录用于定位职责，不表示每项都要立即实现。基础能力设计覆盖现有 Portal 的全部相关代码和消费者，完整边界见[Portal 基础能力架构](capabilities/portal-foundation.md)；业务流程与服务端接入按实际交付补齐所需契约。已有基础组件、工具与支撑代码按本文归属复用，具体取材入口见[基础代码来源与迁移对照](notes/portal-foundation-inventory.md)。

图中组件为已识别的复用单元示例，完整来源与责任归属在对照文件中。基础能力按现有用途完整纳入设计，开发顺序由具体实施批次决定，目录在对应代码进入工程时创建。不能以尚未排入某一批开发为由省略能力、消费者或迁移归属。

`app/` 中的账号、首页、设置和对话入口各自维护自己的功能与交互，不共用一个覆盖全应用的状态对象。只有 `bootstrap/`、根组件与导航注册承担全应用组装；下层代码不依赖它们。领域专属页面和卡片留在 `domains/<领域>/`，由应用导航或对话入口接入。

通用工具可以是单个文件；组件或能力存在多个协同文件时使用目录。不要求一个函数一个目录，也不要求每个模块生成同样的文件集合。

工程配置与辅助文件也有固定归属：

| 内容 | 位置与职责 |
|---|---|
| 依赖与版本锁定 | 根 `package.json` 与工程采用的锁文件；只加入实际接入代码需要的包和运行依赖 |
| TypeScript、编译与模块解析 | 根 `tsconfig.json`、`babel.config.js`、`metro.config.js`；`@/` 对应 `src/`，实际使用该别名的编译和测试入口保持一致 |
| 导入与代码检查 | 根 ESLint 配置及需要的 `scripts/` 检查；按本文的单元边界配置 |
| Jest 配置与运行环境 | 根 `jest.config.js`、`jest.setup.ts` 等实际需要的配置文件；平台替身只留在测试环境 |
| 测试数据与渲染辅助 | 单个用例的 fixture 随测试；确有共同消费者时放 `__tests__/_fixtures/` 或 `_helpers/` |
| Web 预览接入 | 由原有 `website/` 宿主维护自己的依赖和编译配置；迁移仍被其使用的组件时同步核对，原生测试不能证明 Web 接入正确 |
| 功能设计与开发说明 | 引用所属架构、模块契约和代码入口；工程内说明只补充实际运行与接线信息 |

## 2. 基础组件与 UI 复用

### 2.1 复用来源

| 内容 | 使用与维护位置 |
|---|---|
| 基础按钮、输入、列表原子、主题、颜色 token、图标等设计系统内容 | 通过 `@unif/react-native-design` 的公开入口使用，版本由工程依赖锁定 |
| Portal 自有、可跨场景使用的布局、列表组合、弹层、图片预览、Markdown 等 | `components/` 中的对应单元 |
| 消息气泡、附件展示、输入区、确认展示等聊天 UI | `components/chat/`；每个可独立使用的组件有自己的公开入口 |
| 键盘容器、输入区域避让和关联 hook | `components/keyboard/`；状态只服务于键盘布局与交互 |
| 账号、首页、设置等特定应用功能的表单或组件 | `app/` 下的所属功能 |
| 客户、订单、拜访等业务卡片和表单 | 所属领域模块的交互代码 |
| 相机宿主、地图视图等与设备能力直接相关的 UI | 所属 `capabilities/` 单元 |
| WebView 与 H5 协议处理 | `integrations/h5/` |

设计系统继续由组件库维护，Portal 不复制包源码，也不为统一导入路径再包一套同名 Button、Input 或主题 API。Portal 特有的组合组件、默认交互适配和测试随其所属单元迁移。

共用组件通过 props、事件回调和必要的展示类型接收数据，不读取业务 store，不查询客户、提交订单或保存会话。确认组件展示内容、收集用户动作；需要确认什么、动作是否已经表达确认以及随后执行什么，由场景维护。

导航相关的页面布局与弹层保留其视觉和交互用途，路由参数、页面注册与具体导航动作由入口适配。主题和键盘 Provider、Toast 等应用所需宿主由应用组装；单个组件测试只提供它实际需要的轻量宿主。

组件库已有同等功能时直接复用。确需新增 Portal 组件时，说明它补充的交互或组合职责；不将只被一个场景使用的卡片提前提升为全局基础组件。已有中文展示、主题和可访问性语义在迁移中保持；行为改变由对应需求与验收定义。

### 2.2 聊天 UI 与业务逻辑

聊天展示可以被不同业务领域复用，其展示契约属于组件自身。服务端流事件到展示数据的转换留在 `integrations/agent/` 与 `app/chat/` 各自负责的接入、交互代码中；领域结果的呈现由所属领域的交互代码提供。

组件名称中的 Message、Task、Tool、Confirmation 等只描述展示用途，不赋予组件发起模型、工具或业务调用的职责。可选回调只在所属场景已经定义该动作时接入，不能因为组件支持一个按钮就新增重试、提交或其他操作。

## 3. 工具、常量、类型及其他文件的归属

| 文件角色 | 默认归属 | 公开与共享规则 |
|---|---|---|
| 通用计算、日期解析、字符串或文件名处理 | `utils/` 下按实际用途命名的文件或小单元 | 不访问网络、设备、持久存储或业务 store；时间和随机行为在测试中可控制 |
| 功能内部的转换、整理、校验辅助函数 | 所属功能内部 | 先保留为普通函数；只有实际消费者需要才公开 |
| 通用 React 生命周期、倒计时等 hook | `hooks/` | 不嵌入业务请求、选择规则或全局业务状态 |
| 功能或组件专属 hook | 所属功能或组件内部 | 与它维护的状态和生命周期放在一起 |
| 设备操作、文件读写、键值存储、日志运行代码 | 对应 `capabilities/` 单元 | 明确副作用和可替换的外部依赖，不以“工具函数”名义绕过边界 |
| HTTP、流式协议、H5 桥接等适配 | 对应 `integrations/` 单元 | 协议差异在适配处收口 |
| 功能公开输入、输出、错误及必要状态 | 所属单元的 `types.ts`；可执行契约按开发规则保持单一源 | 消费者从功能公开入口取得，不移到全局 `types.ts` |
| 组件 props 和展示类型 | 对应组件的 `types.ts` | 只公开消费者需要的类型；私有子组件类型留在所属单元内部 |
| 外部接口原始 DTO、码表、字段映射 | 使用该接口的功能适配器内 | 原始协议和 Portal 功能契约分别表达各自语义，由适配代码连接 |
| 模块固定值、存储 key、文件用途标识 | 所属单元的 `constants.ts` | 同一含义只维护一份，通过所属模块的必要公开入口复用 |
| 数据库表结构、业务 SQL、表内数据含义 | 使用 SQLite 的功能模块 | SQLite 基础能力不维护全应用的业务表清单 |
| 构建环境和应用级配置 | `config/`；由应用组装读取并向具体依赖传入必要字段 | 功能不读取整份应用环境配置；接口路径留所属接入代码 |
| 可变偏好、草稿、选择和业务进度 | 所属功能或场景的状态代码 | 不作为常量或配置保存；持久化由该功能的已确认需求决定 |
| 样式、中文提示和静态资源 | 优先随所属组件或功能维护；应用共用资源放 `assets/` | 主题 token 仍取设计系统，领域文案不汇入全局提示字典 |
| 环境、静态资源或第三方模块的补充声明 | 确有编译需要时放 `types/*.d.ts` | 不存放客户、商品、设备结果等业务或能力契约；不以宽泛 `any` 掩盖契约缺口 |

角色文件按[文件开发规则第 3 节](PORTAL_DEVELOPMENT.md#3-常量类型变量与文件拆分)维护：存在显式类型、命名固定值或样式定义时，分别放入所属单元的 types.ts、constants.ts、styles.ts；没有对应内容不创建空文件。运行期变量保持原函数或实例作用域，全应用共用内容仍按语义归属，不汇集成全局常量或类型总入口。

TypeScript 的 interface、type、同源派生与命名要求见[文件开发规则](PORTAL_DEVELOPMENT.md)，不另行维护一套写法。

类型、运行时校验和模型 Schema 的同源方式遵循平台架构第 6 节。设计中的代码契约在对应模块维护，实现后以所属代码为事实来源；本文不另建一份字段全集。

## 4. 公共入口与依赖方向

| 使用方 | 可以依赖的内容 |
|---|---|
| 应用组装与导航注册 | 各功能的公开接口、必要宿主、配置与具体适配实现 |
| 页面、对话等入口 | 所属场景或查询功能、展示组件及必要的输入转换 |
| 场景组合 | 被组合功能的公开接口，负责步骤、交互和确认 |
| 独立功能 | 自己的契约、普通辅助函数，以及显式提供或正常导入的必要公共依赖 |
| 通用组件和 hook | 组件库、React 与必要 UI 依赖、其他公开 UI 单元、通用辅助及必要日志接口；不读取应用或领域业务状态 |
| 基础能力、外部适配 | 对应 SDK、协议代码和必要公共支撑能力；不反向依赖页面或具体业务场景 |
| 通用工具 | 与用途直接相关的基础计算代码；不依赖组件、应用组装和业务模块 |

模块间使用明确的公开文件或小型 `index.ts`。不建立导出全部组件、工具、领域或设备能力的总 barrel；使用一个基础组件不应因此加载全部业务代码。内部文件可以按普通相对路径协作，不对外导出私有辅助实现。

日志的常规调用与全局捕获安装、文件存取分别提供必要入口，组件使用日志只依赖常规调用入口。

同一层的两个单元可以通过公开接口形成必要、无循环的依赖，例如 Sheet 使用键盘 UI 单元。没有“同层一律不能使用”的额外限制。两个业务功能共同完成场景时，把协调留给场景，不相互驱动对方的状态。

`import type` 仍算依赖。通用组件不能通过导入领域私有类型取得业务状态结构；需要的展示类型由组件定义，入口完成必要投影。确有共同语义的公开契约可从拥有它的功能引用，不因相似字段就新增全局类型仓库。

需要身份、HTTP 客户端或原生依赖的功能，通过普通参数、小型依赖对象或所属适配器接入。应用组装连接真实实现；不要求通用依赖注入容器、事件总线、能力注册中心或运行时插件框架。

工程开始接线时，`AGENTS.md`、路径别名及导入检查同步采用本目录规则。优先使用现有 TypeScript、ESLint 导入约束和静态引用工具检查跨界、私有深路径与循环依赖；工具配置维护可执行规则，文档解释职责。不复制另一套按旧模式目录或固定文件模板判断合法性的规则。

## 5. 基础能力与资源归属

拍摄与媒体选择、定位与地点查询、地图与选点、SQLite 与文件存取、扫码、蓝牙、分享、语音及系统支撑的完整职责、组合和消费者在[Portal 基础能力架构](capabilities/portal-foundation.md)维护。某项能力分散在旧页面、工具或业务目录中时，也按完整调用链纳入，不只盘点同名文件夹。

每项现有用途都要明确是独立能力、客户端组合、交互入口、领域适配还是未接入占位。普通功能与复杂组合可以在同一模块内分别验证；SDK 全集不等于产品需求，已有组合也不能因职责拆分而丢失。

平台相关实现留在对应能力或 UI 单元内部。继续被 Web 预览使用的代码应有实际可用的 Web 实现或明确表达支持范围的适配，不以成功替身假装设备操作已经完成；测试替身与正式平台实现分开。原生配置和依赖变动通过真实构建与设备验证确认。

## 6. 基础代码迁移与定向验证

迁移按可独立使用的单元进行：代码、必要类型和常量、样式、实际资源、定向测试以及必须的宿主接线一起处理。现有实现已符合职责时复用；有业务状态或外部协议混入时，只调整阻碍边界的部分。旧业务流程及其自动行为不因基础代码迁移而进入新规范。

迁移清单用于定位来源和检查依赖，不替代目标契约。具体执行批次说明纳入哪些单元、依赖接到哪里、相关消费者怎样验证；不要求等待整个营销领域或所有服务端契约完成。

测试按 `src` 中的归属在 `__tests__/` 下组织，文件名能定位被测能力或行为。一个功能存在多项独立能力时，分别运行实际受影响的测试文件；不把“所属模块相同”当作全部重跑的唯一理由。仅本测试使用的 fixture 与该测试放在一起，`_helpers/` 只收实际共用辅助。

| 改动 | 本地优先验证 | 必要的补充验证 |
|---|---|---|
| 普通工具或通用 hook | 对应输入输出、边界或生命周期测试 | 返回语义变化时验证实际消费者 |
| 基础组件 | 组件 props、展示、交互与中文提示 | 受影响的实际组合；布局、键盘、手势等补界面或设备验证 |
| 单个能力内部实现 | 该能力在替代外部依赖下的行为 | 受影响的适配、场景、H5 消费者与宿主接线 |
| 公共类型或常量 | 类型检查及生产方、消费者的相关用例 | 类型检查识别不了的码值、单位、默认值等语义需对应断言 |
| 宿主、初始化、共享 UI 状态 | 状态读写者与入口接线测试 | 多实例、切换、卸载及实际平台行为 |
| 原生 SDK 或平台适配 | 适配契约和相关上层调用 | 相应平台构建、真机；受影响的 Web 预览接入 |

通过明确测试路径和静态引用定位消费者。Jest 的相关测试选择可以辅助缩小范围，H5 协议、宿主注册、跨仓契约等关系另按对应设计补齐。发现选择范围不完整时扩大到相关组合或领域，并修正缺失关系；不能仅凭一个静态命令宣称影响已经覆盖。

引用外部组件库时，Portal 保留证明自身使用方式、组合及宿主接线的测试；组件库内部行为由其所属工程验证，不在迁移中复制成另一套库测试维护来源。系统合并与发布继续执行实际工程配置要求的完整检查。

后续开发一个单元时，主要读取本文件中相关归属、该单元契约、实现、直接依赖与对应测试。基础代码来源对照、其他领域文档及模型评测仅在当前变化确实涉及它们时读取。目录和测试组织的收益在实际变更中按[平台架构第 8 节](ARCHITECTURE.md#8-成本与效果验证)测量。
