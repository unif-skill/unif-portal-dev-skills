# Portal 文件开发规则

本文规定采用新架构的 Portal 客户端在新增、修改、移动、重命名和删除工程文件时遵循的规则。目录归属见[工程组织](PORTAL_STRUCTURE.md)，能力边界见[基础能力架构](capabilities/portal-foundation.md)，业务契约与状态原则见[平台架构](ARCHITECTURE.md)。

这些是客户端工程规则，不把 TypeScript 文件名或 React Native 目录套用到 Agent、Channel、CLI 的其他语言实现。原工程的参考代码按目标职责迁移；迁移范围之外的代码不因一次文件修改自动全仓重排。

## 1. 文件变更入口

修改 Portal 源码及其配套类型、常量、样式、测试、配置、资源接线前，使用 `portal-development` 技能，按本次文件所属类别读取本文相关规则。新模块、公共契约、状态归属或场景职责需要设计时，同时使用 `architecture-design`；已有契约下的内部等价修改不重复开展完整架构设计。

开发前定位本次功能契约、所属单元、已有公开入口、实际消费者和对应测试。新增文件落在已确定的单元中；新增单元时说明其独立职责和使用方，不从页面名称或 SDK 包名直接推导一套业务模块。

用户已明确的需求和契约限定实现范围。文件拆分、命名统一和代码迁移不增加重试、自动提交、缓存、恢复、确认或新接口调用。

## 2. 各类代码的开发规则

| 类别 | 必须维护的边界 | 变更时核对 |
|---|---|---|
| `components/` | props、必要展示类型和事件回调；组件自身的 UI 状态 | 复用现有设计系统与组合组件；不读取领域 store 或发起业务请求；确认 UI 不承担场景确认规则；渲染和交互测试可使用轻量宿主 |
| `capabilities/` | 独立操作、输入输出、错误、副作用和资源生命周期 | SDK 或外部依赖可替换；调用、取消和释放归属于本次操作；宿主和平台实现按能力接线；一个能力修改只验证真实影响 |
| `domains/` | 领域功能、场景组合、业务交互与所属状态 | 功能入口、准备/确认/提交的责任明确；页面和对话复用同一链路；最终规则与业务事实仍由业务系统处理 |
| `integrations/` | 所属外部协议、原始 DTO、请求/回包转换和接入错误 | 契约与真实外部能力一致；按所属接口码表解释结果；不在转换中新增流程、补造身份或改写成功语义 |
| `app/` | 应用功能与入口；bootstrap 和导航负责真实组装 | 页面保持输入和展示适配；账号、设置、对话等各自维护状态；下层不反向读取启动代码或全应用状态对象 |
| `hooks/` | 与领域无关的通用 React 行为 | 功能专用 hook 留在功能内；不在公共 hook 中隐藏业务请求或设备操作 |
| `utils/` | 通用计算或格式处理 | 不访问网络、设备、持久存储和业务 store；模块私有辅助优先留所属模块，不因为函数短小就移入全局工具 |
| `config/` | 构建环境和应用配置的明确来源 | 应用组装向依赖传入必要字段；运行期状态、业务表结构和全部接口路径不汇入全局配置 |
| `types/` | 确需全局补充的环境、静态资源或第三方声明 | 业务模型、组件 props 和能力结果不放这里；不通过宽泛声明掩盖真实类型错误 |
| 测试、脚本、资源与原生配置 | 服务于明确功能或工程接入 | 测试按所属单元定位；脚本和平台配置遵循其工具要求，不机械套用 TypeScript 源码文件规则 |

## 3. 常量、类型、变量与文件拆分

### 3.1 固定文件角色

下表用于手工维护的源码单元。构建环境和品牌等配置入口按用途保留 env.ts、brand.ts 等配置文件名；环境补充声明、工具约定文件与生成文件遵循各自要求，不按其中出现 const 或 interface 反推改名。

| 内容 | 文件位置 | 判定条件 |
|---|---|---|
| 显式声明的接口、类型别名和联合类型 | 所属单元的 `types.ts` | 包括 props、输入输出、错误、内部结构及事件类型；对象结构使用 interface |
| 命名的固定值、码表、枚举值集合、默认配置值与固定映射 | 所属单元的 `constants.ts` | 值不依赖本次调用、当前实例、当前用户或运行期资源 |
| React Native 样式定义及主题样式工厂 | 所属组件或交互单元的 `styles.ts` | 尺寸、状态等运行期样式输入仍由调用处传入，组件不复制主题 token |
| hook 实现 | `useXxx.ts`；包含 JSX 时用 `.tsx` | 专用 hook 放所属单元，通用 hook 放 `hooks/` |
| 普通逻辑、输入转换与内部辅助 | 说明其用途的 `.ts` 文件 | 不为文件分类额外创建 helper 类、服务类或公共抽象 |
| 可执行 Schema 或校验 | 所属单元的 `schema.ts` 或该单元已采用的生成文件 | 是否需要由边界契约决定；不为补齐文件集合引入校验框架 |
| 跨文件共享的可变状态与资源 | 所属功能的 `state.ts`、具体 store 或资源实现 | 必须有实际读写者、初始化和释放责任；不放 constants.ts |
| 私有局部变量 | 原函数、组件或 hook 内 | 保持与本次调用或实例相同的作用域，不创建统一 variables.ts |

角色文件有实际内容时才创建。同一单元内使用固定名称 `types.ts`、`constants.ts`、`styles.ts`，不交替使用 `type.ts`、`interfaces.ts`、`const.ts` 等近义名称。单元内部确有独立维护的子单元时，文件角色跟随该子单元，不让一个 types.ts 或 constants.ts 汇集整个领域。

原本只有一个实现文件的普通工具可以保持单文件。出现需要独立维护的显式类型、命名常量等配套内容时，以该工具名称建立单元目录，放入实现和实际需要的角色文件；不为每个内部辅助函数单独建目录。

例如 CellList 单元的组件放 `CellList.tsx`，props 和条目类型放 `types.ts`，公共出口放 `index.ts`。它没有自己的命名固定值时，就没有 `constants.ts`；不因为另一个组件有此文件而补一个空文件。

### 3.2 const 与固定常量的区别

`const` 只表示变量绑定不能重新赋值，不决定文件归属。根据输入计算的结果、当前选中项、ref、Map、SDK 实例和请求控制器仍属于逻辑、状态或资源。把这些值移到 constants.ts 会改变调用或实例间的共享关系，不属于命名整理。

不要求把所有字面量抽成常量：数组长度为 0 的检查、循环递增、普通布尔分支等可以直接表达。具有业务、配置或可复用展示含义的固定值使用命名常量，并放到所属 constants.ts；具体取值必须来自已采用的需求或契约。

### 3.3 类型与可执行契约同源

手写对象结构定义在 types.ts 中使用 interface；函数签名需要明确对象结构时引用相应接口，不在多个实现文件重复写同一结构。基本类型、泛型参数和就地类型推导不需要额外创建别名。

已采用可执行 Schema 或代码生成的契约，以其明确的代码源为准：types.ts 引用、派生或导出所需类型，不重复手写字段；生成文件遵循生成器的固定命名，修改源后重新生成。接口作为源生成 Schema 的契约同样保留单一源。不能为满足“类型单独放”而维护另一套结构。

`type` 用于基本别名、字面量集合、已命名接口的联合及必要推导类型。第三方公开类型直接引用，外部 DTO 的字段名遵循协议，不因本工程命名规则改写线上协议。

内部类型可以从 types.ts 导出供本单元文件使用，但不因此进入单元公共 index.ts。类型依赖同样遵守架构边界，不能用 import type 穿透另一模块的私有状态。

## 4. 命名与公开出口

| 对象 | 统一规则 | 示例或说明 |
|---|---|---|
| React 组件及组件单元目录 | PascalCase，主文件与主组件同名 | `CellList/CellList.tsx` |
| 领域、能力、接入与普通功能目录 | lowerCamelCase | `marketing`、`imagePicker`、`keyValue` |
| 普通函数、变量与对应主实现文件 | lowerCamelCase，以实际用途命名 | `getProductsByIds`；函数文件与其主操作同名 |
| hook | use + PascalCase 主体，文件同名 | `useCountdown.ts` |
| interface、类型别名、类 | PascalCase，不添加 I 前缀 | `CellListProps`、`CameraResult`；这些示例不新增对应契约字段 |
| 命名的固定常量 | UPPER_SNAKE_CASE | 固定限额、默认值与码值集合使用一致形式；对象成员按语义或外部契约命名 |
| 事件回调 props | on + 动作；表达用户请求时明确请求含义 | `onSelect`、`onRequestDelete`；内部处理函数可使用 handle + 动作 |
| 测试文件 | 被测单元或行为名称 + `.test.ts` / `.test.tsx` | 与实际被测公共入口或行为对应 |
| 平台适配 | 主文件名 + `.native` / `.ios` / `.android` / `.web` + 扩展名 | 按实际平台差异使用，不生成没有实现意义的空版本 |
| 工具约定文件和生成文件 | 保留工具要求的固定名称 | package.json、tsconfig.json、index.ts 等不套主组件命名规则 |

选择、查询、准备、确认、提交和保存是不同操作，函数名与副作用相符。名称变化若影响公开消费者，同步导入和契约；不为了统一命名擅自更改业务字段、协议标识或已确认的功能语义。

跨单元调用使用明确的公开文件或小型 index.ts，具名导出实际公共接口。公共入口不导出全部内部类型、常量和辅助函数，也不串联全平台的大型 barrel。同一单元内部允许普通相对导入。

## 5. 规则执行与定向验证

技能负责读取依据和指导判断，工程检查负责能确定执行的规则。采用本规则的目标项目在 AGENTS.md 中维护简短入口：源码及配套文件变更前使用 portal-development，并指明所用工程规则版本；详细规则通过技能或规范引用读取，不在 AGENTS.md 再复制一份。

工程接入时用现有 TypeScript、ESLint 和必要的静态分析检查类型、命名、导入方向、私有深路径、循环依赖及角色文件组织。使用 AST 区分类型声明、固定值、局部变量和资源，不用“遇到 const 全部搬走”的文本规则。固定值的业务含义、状态归属和副作用是否必要仍需依据契约审查。

新增单元同时具备可使用的公开入口、真实依赖接线及相应验证；不以有目录或编译成功作为功能完成依据。调整类型、常量或文件位置时按静态引用核对消费者，补充宿主、H5 协议与跨仓契约等非静态关系。

本地优先运行该功能、适配及实际受影响组合的测试；系统合并和发布按工程既定 CI 验证。文件组织变化不要求默认重跑整个领域 Jest，也不能以只改类型或常量为由跳过实际语义影响。

技能本体、规范快照和模型评测在 `unif-portal-dev-skills` 仓库维护。规范快照由本项目的源文件生成，使用时按变更类别读取相应章节；源码阅读记录和 evals 不进入默认开发上下文。
