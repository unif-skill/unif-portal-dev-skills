# 技能选择

| 请求 | 选择 | 理由 |
| --- | --- | --- |
| 1. 修改现有组件的 props 和主题样式 | portal-development | 涉及新 Portal 客户端源码、类型和样式修改；描述未表明涉及公共能力契约或架构调整，无需据此加入 architecture-design。 |
| 2. 移动图片选择能力文件并更新 H5 调用入口的导入 | portal-development | 文件移动和入口导入修改属于 Portal 源码修改，单纯位置及引用调整未体现能力契约或职责变更。 |
| 3. 增加资源声明并修改 Metro 配置 | portal-development | 资源声明、配置和资源接线均在该技能明确覆盖的修改范围内。 |
| 4. 仅讨论跨领域业务职责划分 | architecture-design | 跨领域职责划分属于架构和业务模块设计，且纯讨论不触发 portal-development。 |
| 5. 业务用户说“开始今天的拜访” | 两者均不使用 | 这是业务用户对话，两项技能均明确排除此类请求。 |
| 6. 修改 Python Agent 服务的任务函数 | 两者均不因当前请求而触发 | portal-development 排除其他语言的后端工程，而普通任务函数修改本身未体现 architecture-design 所要求的架构、契约或场景设计事项。 |
| 7. 只运行已给定的测试命令 | 两者均不使用 | 两项技能均明确排除仅运行给定测试且不修改文件的请求。 |
| 8. 新建公共能力，同时改变场景状态归属 | architecture-design 和 portal-development | 公共能力及场景状态归属需要架构设计判断，后续 Portal 源码修改也必须使用适用开发技能。 |

这些选择不能证明目标工程已强制启用文件组织和导入静态检查。技能描述和项目入口约定只能说明技能适用范围及文件修改前的使用要求，没有提供静态检查配置、执行接线或强制门禁的证据。确认强制启用还需检查目标工程实际的检查规则、执行入口及 CI 门禁；本次仅作书面选择，未进行这些检查。
