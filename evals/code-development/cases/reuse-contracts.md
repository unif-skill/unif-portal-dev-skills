# 复用与输入契约

这是已按目标架构开发的合成 Portal 工程。请依据提供的技能材料审查下面两个独立的等价整理，给出采用或保留的具体部分、关键代码或边界，以及受影响的验证。只输出方案，不修改真实工程或执行外部操作。题设中的库能力是本题完整依据，不代表实际 SDK。

## A：相似实现的共享范围

项目已采用一个工具库：`unique(values)` 按首次出现顺序删除重复字符串，`hasOwn(object, key)` 只判断自有属性。

- 两个配置读取器各自对字符串标识列表去重，契约都是保留第一次出现的顺序。
- 操作输入中的标识列表要求全部非空且不得重复，重复时返回输入错误，不调用提交接口。
- 三个枚举校验器都用已定义的值集合判断成员；应用与外部接入共享同一份公开身份字段类型。
- 拍摄和图片选择都把媒体交给本地文件操作。拍摄 URI 只接受本地文件；图片选择 URI 还允许平台提供的内容引用。两者分别持有操作状态，退出、取消和失败清理按各自契约处理。

整理建议是把所有去重都换成 `unique`，统一身份类型和枚举判断，并抽一个同时管理 URI、状态、复制及清理的媒体基类。请逐项审查；必要时给出范围更小的复用方式。

## B：接口映射与缓存读取

配置接口允许展示标题缺失。现有接入代码把缺失标题映射为空字符串，且不丢弃该行。缓存契约保存映射后的 `Item[]`，其中 `id` 是非空字符串、`title` 必须是字符串；缓存记录还包含 `ownerId`，只允许当前身份读取。缓存读取的运行时结果是 `unknown`，无效记录按未命中处理，不返回部分列表。

有人准备用同一个转换函数处理接口和缓存：读取缓存后直接 `as Item[]`，或者对每个字段调用 `String(value ?? '')`，然后复用接口的缺值映射。他认为 TypeScript 已经定义了类型，统一函数可省去缓存校验。

给出缓存边界的处理方式和验证样本，包括合法空列表与空标题、非法成员、错误身份及缺失标题；同时说明接口侧缺标题行怎样处理。工程没有约定新增 Schema 框架，本次不改变数据契约。
