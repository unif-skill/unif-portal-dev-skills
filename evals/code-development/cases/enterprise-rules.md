# Portal 企业规范的应用

这是采用本插件规范的合成 Portal 客户端。通用流程已安排实施与审查，但企业技能必须在相关步骤应用。只输出审查结论、测试方案和规范依据，不写业务源码、不执行工程、Git或外部操作。

## 工程事实

1. 组件 CellCard 被两个营销入口复用。实现文件含手写 `type CellCardProps = { title: string }`、命名固定值 `EMPTY_LABEL = '暂无'`、普通组件逻辑和主题样式工厂。开发者建议把 props、固定值、样式都留在实现文件；另一个人建议统一移入全局 types.ts/constants.ts，把每个函数拆成目录。组件还通过 useRef 持有本实例 Map，被建议一起搬到 constants.ts。
2. 领域客户查询在营销内共用，两个消费者分别是 H5 入口与普通页面。查询函数每次按参数读指定页；后端契约明确数值 code 200 成功，列表字段缺省和行内缺少展示名称允许显示暂无，写入操作另要求真实客户标识。有人建议把查询移入全局 utils；列表字段缺省时改为失败，随后补发详情请求；名称缺省时用列表索引作为后续写入标识。
3. 此次测试只 mock 查询函数自身再断言预设成功，覆盖报告排除了实际查询源码；静态相关测试命令未列出 H5 入口，团队却声称它已覆盖全部消费者和真实设备行为。
4. 一个设备能力文档列出公开 prepare、query 和 UI 宿主；实际协议只确认一个查询 HTTP 请求，prepare 是普通客户端初始化，纯数据调用不需要宿主。建议按 export 自动增加 prepare HTTP/H5/tool 三类入口，并强制纯查询先挂载 UI。

请按适用工作加载企业技能和对应资料，分别指出上述建议中的问题与可采用做法，列出真实实现/消费者需要验证的内容，并说明通用流程是否能代替企业规则。既有契约已完整，不重复访谈或安排另一套通用开发流程。
